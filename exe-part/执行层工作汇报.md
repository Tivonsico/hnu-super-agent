## 二、实现了哪些功能

### 1. Router：判断消息包去向

- 看门狗调用 `notify` 后，宿主先登记接管这个包，同一个包重投时直接回 `REPLAYED`，不会再判断一次。
- Router 读包原文和可见工单的标题、简述，主题相近时再打开工单文件核对，然后三选一：
  - **新建**：调用 `createTicket` 建单，宿主随后派 Worker。
  - **归入**：最终回复一个 `{ticket_id, package_ref}`，宿主把包交给那张工单的 Worker。
  - **忽略**：回复 `ignore`，本轮结束。
- 拿不准时可以发 `ROUTE_REVIEW` 通知问用户，用户答复后宿主带着答复让 Router 重新判断。
- Router 判断完就结束，不等 Worker，也不汇总结果。这是 F 会推翻早期方案后的最终说法。

### 2. Worker：处理一张工单

- 每张工单固定一个 Worker 会话 `worker-<工单号>`，后续输入都接着用这个会话。
- 首次派工时 Worker 还没在干活，宿主开一轮新的（queue）。之后归入的新包和用户的补充、反馈、合并都用 steer 交付：Worker 在当前小步骤做完后就能看到，不用等整轮结束，也不会被硬生生打断。这样新输入能及时纠偏，交付路径也只有一条。
- Worker 能写五种节点：`input`（登记归入的新包）、`result`（成果）、`blocked`（卡点）、`unblocked`（解除）、`note`（本轮笔记）。
- 成果文件由宿主从工作区发布到 `superdot/artifacts/`。Note 草稿由宿主核对后发布到 `superdot/memory/notes/`。
- 需要用户时发通知：成果待核对发 `RESULT_READY`，缺文件发 `INPUT_NEEDED`。

### 3. 用户对工单的操作

`POST /api/tickets/actions` 支持接口文档里的全部操作：

| 操作 | 宿主做什么 |
|---|---|
| 补充 `supplement` | 写 `input` 节点，交给 Worker。 |
| 反馈 `feedback` | 写 `feedback` 节点并引用原成果，交给 Worker。 |
| 终止 `stop` | 写 `stop` 节点，取消 Worker，工单从候选中隐藏。 |
| 恢复 `resume` | 写 `resume` 节点，工单重新可见，接着用原会话。 |
| 异常接续 `recover` | 写 `recover` 节点并引用中断节点，交给 Worker 接着做。 |
| 合并 `merge` | 先取消源单的 Worker，再交给目标单的 Worker 调用 `mergeTickets`。 |
| 确认 `confirm` | 宿主直接写 `confirm` 节点，返回新节点号。 |

同一个 `operation_id` 重复提交回 `REPLAYED`，内容不同回 `CONFLICT`。

### 4. 通知与下载授权

- 通知的登记、查询、处理、回执投递，Router、Worker、Dreamer、数据库共用一套。
- 下载流程按合同顺序：Worker 写 `blocked` 并发 `INPUT_NEEDED`，用户选 `allow` 后宿主下载文件，再把文件路径交给 Worker，Worker 写 `unblocked` 继续做。选 `decline` 时宿主把答复原样交给 Worker。

### 5. 对外 HTTP 接口

`notify`、工单操作与确认、单个工单和工单列表、通知列表、处理通知都已实现，错误码对应的 HTTP 状态码与接口文档一致。

### 6. 提示词和上下文

- Router、Worker 各有一份角色模板（`prompts/router.md`、`prompts/worker.md`），启动时自动接上用户的 `MEMORY.md`。会议定的是"每次启动前加载角色模板和 MEMORY.md"。
- 每轮交给模型的只有一段 JSON 绑定，写着本轮的包号或工单号、路径和输入。工单正文由模型自己用 `read` 打开，不预先塞进上下文。

## 三、权责边界怎么保证

提示词只能告诉模型"不该做什么"，模型仍然可能做。所以每条边界都在工具层再限制一次，做不到的事模型根本拿不到工具。

| 角色 | 提示词里写明 | 工具层限制 |
|---|---|---|
| Router | 只判断去向，不执行任务，不写工单。 | 只给 `read`、`skill`、`bash`、`job_output` 四个原生工具，没有写文件、改文件的工具。`bash` 里出现重定向、`rm`、`mv`、`cp` 等写入命令时直接拒绝。 |
| Router | 建单前先查候选。 | `createTicket` 要求本轮已调用过 `readCandidateTickets`，否则回 `INVALID_INPUT`。 |
| Router | 包号、工单号用绑定里的原值。 | `createTicket` 只接受本轮绑定的包号和预分配的工单号。 |
| Worker | 只处理本工单。 | `appendTicketNote` 只接受本单号，节点号必须以本单号开头。 |
| Worker | 引用只用合同里的几种。 | `refs` 每一项都按 06 的 `EvidenceRef` 检查，多一个字段、少一个 `id` 都会退回。 |
| Worker | 成果放 `artifacts/`，收尾写 Note。 | 成果文件不在 `workspace/artifacts/` 回 `REF_NOT_FOUND`。Note 草稿缺失或字段和当轮不符也退回。 |
| Worker | 合并由目标单执行。 | `mergeTickets` 只允许目标单的 Worker 调用，参数要和用户提交的原操作一致。 |
| Worker | 下载要用户授权。 | `askDownloadFile` 在用户 `allow` 之前一律回 `AUTHORIZATION_REQUIRED`。 |

工具退回时会附一句 `detail` 说明原因，例如"新版成果要用新文件名"，模型看了能自己改正，不会原样重试。

### 3. 和接口文档不一致、需要修改的地方

1. **`notify` 回执返回得太晚。** 接口文档的要求是保存接管记录后先回执，再异步派 Router。现在要等 Router 判断完、甚至 Worker 首轮做完才返回，看门狗会等很久，可能超时重投。重投会回 `REPLAYED`，不会重复处理，但等待时间不合理。修改方法是先保存待执行任务再回执，同时补上程序重启后把没做完的任务接着做。
2. **归入前没有复核目标单是否可见。** 接口文档要求归入投递前由宿主复核目标可见性。现在只检查了工单是否存在，如果 Router 判断期间用户终止了目标单，新包仍会交给它。`TICKET_HIDDEN` 错误码已定义但还没用上。
3. **合并的收尾情况没有处理。** 接口文档要求"目标单提前结束、合并还没开始时，释放源单并通知合并未完成"，这一条没有实现。另外，合并期间宿主只取消了源单的 Worker，没有拦住这段时间里发给源单的新输入。

以上三处都不依赖其他模块，下一个节点就可以改。

## 七、代码是怎么组织的

代码在 `exe-part/hnu-execution/`，一共约 1500 行，分成三层。这个分法照搬了 DSSA 的做法：核心逻辑和 DSH 分开，核心不认识 DSH，所以不连网络也能测。

### 整体结构

```
对外接口（HTTP） ──> 执行宿主 orchestrator ──> 工单 / 通知 / 消息读取
                        │
                        └── 端口 ports ──> DSH 适配 loop（真实模型）
                                       └── 消息层 store（消息层实现）
```

中间那层"端口"是关键。宿主不直接调用 DSH，而是调用一个叫 `AgentLoop` 的接口；消息层也一样，走 `MessageStore` 接口。真实运行时接上 DSH 和消息层，测试时换成假件，宿主本身的代码一个字都不用改。45 项单元测试能不连网络跑完，就是靠这个。

### 几个值得一提的设计

**一、工单是一个只追加的日志。** 工单文件每行一条 JSON，第一行是固定头，后面每个节点追加一行，从不改已有的行。追加时把原文件整个读出来当前缀，在后面加一行再整体换名发布。这样做有三个好处：任何一步都能原样重放而不出错；工单的当前状态（比如是否可见）由从头到尾过一遍节点算出来，不用单独存；中途断了，下次比对内容就知道哪一行还没写，接着写即可。可见性就是这么算的——初始可见，遇到终止、并出变不可见，遇到恢复又变回可见。

**二、所有写入都能重放。** 每一次接管、每一个用户操作、每一个节点、每一条通知，都有一个稳定的编号。编号用内容算出来（`sha256` 取前一截），同样的输入永远得到同样的编号。再写一次时，发现编号已存在且内容相同就跳过，回 `REPLAYED`；内容不同就报 `CONFLICT`。看门狗超时重投、前端重复点击，都不会造成重复处理。

**三、只有 Worker 写业务节点，宿主和 Router 不和它抢。** 这是会议反复讨论后定的"单写者"。宿主只写固定头、会话节点和用户操作节点这类框架性的东西，真正的业务内容全部由 Worker 通过工具写。宿主要让 Worker 做事，是把内容作为新输入发给它，而不是自己去改工单。"提醒 Worker"和"改工单"因此变成了同一件事。

**四、每轮只给模型一段绑定，正文让它自己读。** 交给模型的上下文只有一小段 JSON，写着本轮要处理的是哪个包或哪个操作、文件在哪。工单正文、消息原文都靠模型自己用 `read` 打开。上下文因此很短，也不用在工单变化时反复重拼。这对应会上倾向的"增量 + 事件驱动"，而不是每轮把整张工单塞进去。

**五、边界靠工具，不靠模型自觉。** 第三节已经讲过。这里补一句原理：DSH 的参数校验只认得很基础的格式，06 里"`input` 节点必须引用一个包"这种规则它表达不了。所以这些规则写在工具的执行函数里，模型传了不合规的参数，工具当场退回并说明原因。模型能看懂原因、自己改对，而不是反复撞同一堵墙。

## 八、一句话总结

执行层的主干已经按设计做完并测过，角色边界在提示词和工具两层都落实了。接下来主要是等消息层、数据库、前端到位后联调，同时补齐那几条少见分支的测试，并修掉第五节第 3 点列出的三处与接口文档的出入。
