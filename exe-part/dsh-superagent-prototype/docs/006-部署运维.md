# 006 部署运维

本指南用于安装、配置与运行 dsh-superagent，涵盖账号、启动检查、升级与故障排查，建立在 [001 领域模型](001-领域模型.md) 至 [005 控制面板](005-控制面板.md) 之上。

## 运行内容

- **一个专用的 DeepSeek Harness 配置档**，本指南中称为 `superagent`。它由 Web 配置档模板创建，负责加载本扩展包，并在 `127.0.0.1` 上提供面板。请与你自己日常使用的配置档分开：该插件会改动进程级的 `PATH` 与 git 设置，其进程也需要独立地重启与升级。
- **一个智能体专用 GitHub 账号。** 智能体以该账号发表评论、推送分支、开立拉取请求，所用 GitHub CLI 只以该账号登录。
- **可选：** 一个用于接收群聊请求的飞书机器人。

插件配置只保存状态目录与机器限制。其余一切在面板中设置：仓库与账号在「来源」，许可名单在「策略」，worker 目录与命令在「执行」。

### 权限与隔离

扩展包为执行器定义了 `dsh-superagent-worker`，为主 Session 定义了 `dsh-superagent-router`。它们会出现在 DeepSeek Harness 的预设列表里，但只供 dsh-superagent 使用。不要把它们选给个人 Session，也不要禁用对应的配置行；应用需要靠它们创建与恢复自己的 Session。

在 Web 界面打开一个空白的托管 Session，可能会选中该配置档的默认预设。dsh-superagent 会在首个回合之前把它恢复为按角色区分的预设。

这两个预设都以操作者的操作系统用户身份、在 `danger-full-access` 下运行，并读取已订阅线程上的消息。账号包装脚本只是默认选用智能体的凭据，并不隔离进程。worker 可以按路径执行程序，也能读取操作者的主目录。若需要隔离，请使用一个只存放智能体凭据的专用操作系统账号。

## 前置条件

- Node.js 22.19+ 或 24+、pnpm、git 2.32+、Python 3.8+ 与 tmux
- GitHub CLI（`gh`）2.48 或更高版本。来源的 CLI 字段必须指向 `gh` 或 `lark-cli` 的包装脚本；宿主依赖它们的子命令与输出格式。
- github.com 上的仓库；不支持 GitHub Enterprise Server。若要为每个工单创建一份检出，请保留一份本地克隆，供准备命令从中添加 worktree。若该仓库使用 Git LFS，请安装 `git-lfs`。
- 为 DeepSeek Harness 配好一个模型提供方。除「评估」或「执行」设置另行指定外，dsh-superagent 使用该配置档的默认模型。
- 若接入飞书：`lark-cli`（已在 1.0.90 上验证）以及一个带机器人的飞书或 Lark 应用

## 账号

### 智能体 GitHub 账号

1. 为智能体创建一个 GitHub 用户账号，并授予仓库写权限。GitHub App 不能充当智能体，因为 dsh-superagent 要读取该账号的通知。
2. 为它配一份只使用自身凭据的 GitHub CLI：

   ```sh
   mkdir -p ~/.local/bin
   cat > ~/.local/bin/gh-agent <<'EOF'
   #!/bin/sh
   GH_CONFIG_DIR="$HOME/.config/gh-agent" exec gh "$@"
   EOF
   chmod +x ~/.local/bin/gh-agent
   gh-agent auth login
   gh-agent api user --jq .login
   ```

   以智能体账号登录；最后一条命令会打印它的登录名。dsh-superagent 也用同样的方式读取登录名。

### 飞书机器人（可选）

1. 创建一个具备机器人能力的企业自建应用。授予接收消息事件、读取与发送群聊消息、读取群成员的权限，然后发布应用版本。
2. 为机器人准备一份独立的 `lark-cli` 配置，限定为机器人身份，并配一个包装脚本：

   ```sh
   LARKSUITE_CLI_CONFIG_DIR="$HOME/.lark-cli-dsh-superagent" lark-cli config init --app-id <cli_…> --app-secret-stdin
   LARKSUITE_CLI_CONFIG_DIR="$HOME/.lark-cli-dsh-superagent" lark-cli config strict-mode bot --global
   cat > ~/.local/bin/lark-bot <<'EOF'
   #!/bin/sh
   export LARKSUITE_CLI_CONFIG_DIR="$HOME/.lark-cli-dsh-superagent"
   exec lark-cli "$@"
   EOF
   chmod +x ~/.local/bin/lark-bot
   ```

   第一条命令从标准输入读取应用密钥。务必使用独立的配置目录：`lark-cli` 对每个 app id 只允许一份配置，而你的个人配置里可能已经有该应用的用户登录态。

   宿主会拒绝能够以用户身份行动的 CLI。它从机器人配置中读取 app id、飞书／Lark 品牌以及机器人的 `open_id`。

   两份配置共用钥匙串里的应用密钥条目。若只想移除机器人配置，直接删除其目录即可；不要执行 `lark-cli config remove`，那会动到共用的密钥。

## 安装

在尚未创建 `superagent` 配置档的机器上，把下面这段执行一次：

```sh
npm install -g @deepseek-ai/dsh@0.2.1-rc.3
git clone <this repository> dsh-superagent && cd dsh-superagent
pnpm install && pnpm build
dsh superagent --from-default-profile web --dump-config > /dev/null
dsh plugin --profile superagent add "link:$PWD"
```

上面锁定的版本是公开版本；改用其他版本时，必须满足 `package.json` 中的 `engines.dsh`。

第四条命令依据 DeepSeek Harness Web 模板创建 `~/.dsh/profiles/superagent`；第五条安装本扩展包。设置 `DSH_HOME` 可改变默认的 `~/.dsh` 目录位置。

创建配置档的命令只在全新安装时执行。若配置档已存在，该命令会替换它并删除其中的 `cordis.patch.yml`（含机器配置）。升级时不要使用它。

## 机器配置

把 [examples/profile.cordis.patch.yml](../examples/profile.cordis.patch.yml) 复制到 `~/.dsh/profiles/superagent/cordis.patch.yml` 并覆盖该文件，然后替换其中的每一个 `<placeholder>`。若接入飞书，还要在那里启用 `dsh-superagent-feishu` 条目。`webserver` 条目决定面板端口。

| 键 | 是否必需 | 含义 |
| --- | --- | --- |
| `stateDir` | 是 | 绝对路径：存放数据库、锁文件、`worker-bin` 中的命令垫片、智能体的 git 配置，以及默认位于 `work` 下的工单目录。升级前请备份 |
| `promptMaxChars`, `admissionContextMaxPages`, `admissionContextTimeoutMs` | 否 | 可保存的提示词配置的最大长度，以及一次研判在多长时间内最多读取多少页线程内容 |

首次启动后，可在 **设置 → 部署** 或 DeepSeek Harness 插件管理器中修改机器限制，改动无需重启即刻生效；但那里改不了 `stateDir`。取值非法或出现未知配置键会阻止启动，日志会指出具体是哪个键。

## 启动与停止

```sh
scripts/dsh-superagent start
scripts/dsh-superagent status
```

`start` 在 tmux 会话 `dsh-superagent` 中运行 `dsh --profile superagent`；若使用其他配置档，会话名为 `dsh-<配置档>`。它最多等待一分钟，直到运行时就绪或报出某项安装要求。首次运行会打印缺少的安装信息。它会拒绝重复实例，包括不是通过本脚本启动的那些。

`stop` 与 `restart` 请求优雅关停，并为执行器最多等待五分钟。它们绝不强制杀进程，也不会碰其他 tmux 会话。

`status` 打印进程 id、健康状况与安装问题。若配置档或端口不同，用 `--profile` 与 `--url`，或设置 `DSH_SUPERAGENT_PROFILE` 与 `DSH_SUPERAGENT_URL`。

`status`、`start` 与 `restart` 以四种退出码之一结束：

| 退出码 | 含义 |
| --- | --- |
| 0 | 服务运行正常 |
| 1 | 服务未运行、运行了两份、无响应，或运行时报错；重启有可能修复 |
| 2 | 服务在运行，但运行时之外的某个部件报错，例如来源或策略同步（`sync:<来源 id>`）；重启无法修复 |
| 3 | 服务在运行但等待安装配置；重启无法修复 |

尚在启动中的来源算作正常运行；安装检查未能核验的飞书机器人同样算作正常。

`status` 把出错部件及其细节放在 `errors` 下，把安装要求放在 `setup` 下。`start` 与 `restart` 会把这些问题逐行打印；若服务始终没起来，则以 1 退出。只有主动执行 `stop` 才会暂停自动恢复。

每个配置档把日志与控制文件放在 `.artifacts/` 下：

- 启动日志：`dsh-superagent-<配置档>-<日期>-<时间>-<pid>.log`，其中 pid 属于该脚本；保留最新 20 份。
- 控制文件：`control/profiles/<配置档>/`，包含停止标记、锁文件与进程 id。

打开日志中打印的 URL，然后在侧边栏选择 **Superagent**。

### 每小时巡检

把每小时一次的巡检建在你日常使用的 DeepSeek Harness 配置档里，不要建在 `superagent` 里：智能体服务停掉时，它必须仍能运行。让该配置档中的智能体用下面这段提示词创建一个每小时执行的定时任务，并填好检出路径：

```text
检查 dsh-superagent：在 <检出目录> 中运行 `scripts/dsh-superagent --profile superagent status`。退出码 0：什么都不做，也不要说话。退出码 2：不要重启；把 `errors` 下的每个部件及其细节告诉我，除非同样的内容你已经告诉过我。退出码 3：不要重启；把 `setup` 里说缺什么告诉我，除非你已经说过。若它报告 `manually_stopped: true`，就让它继续保持停止。其余情况（退出码 1）运行 `scripts/dsh-superagent --profile superagent --respect-stop restart`，该命令的退出码含义相同：0 表示已恢复，什么都不用说；2 和 3 按上面处理；若它以 1 退出或出现其他失败，就读取最新的 `.artifacts/dsh-superagent-superagent-*.log` 以及 `docs/006-部署运维.md` 的「故障排查」一节，能修的自己修，然后告诉我出了什么问题、你做了什么。
```

`--respect-stop` 会保留主动停止的状态。只有 `stop` 会写入停止标记，`start` 会清除它。`restart` 不写标记，因此巡检能够把一次因关停超时而卡住的重启拉回来。

## 设置

必须先完成安装配置，才会开始轮询或工作。总览列出缺少的条件并链向对应设置。任何设置改动都会重新跑一次安装检查。若你在应用之外修好了某项（例如 CLI 登录），选择 **重新检查**。

1. **来源。** 设置 GitHub 仓库（格式 `owner/name`）与智能体 CLI，例如 `/home/me/.local/bin/gh-agent`。请求通常经由智能体账号的通知到达。提及该账号的新 Issue 或新评论会在下一次轮询时被收到；而通过编辑已有 Issue 正文补上提及则不会——请改为发一条新评论。若接入飞书，设置机器人 CLI、群聊、每个群聊是「接收全部」还是「仅 @」，以及是否接收私聊消息。
2. **策略。** 两条示例规则可以修改或删除。在 **各来源分别设置** 下加入可以分派工作的 GitHub 账号与飞书用户；名单在有人之前，任何请求都不会变成工单。接入飞书时，可指定一个群聊作为名单同步来源，在启动时以及点击 **立即同步** 时同步。
3. **执行。** 目录根路径与准备命令。若要给每个工单一份仓库检出：

   ```sh
   git -C /home/me/src/widgets fetch --no-tags "https://github.com/$DSH_SUPERAGENT_GITHUB_REPOSITORY.git" "${DSH_SUPERAGENT_GITHUB_PR_HEAD:-HEAD}:refs/dsh-superagent/$DSH_SUPERAGENT_TICKET" &&
   git -C /home/me/src/widgets worktree add -b "agent/$DSH_SUPERAGENT_NAME" "$DSH_SUPERAGENT_DIR" "refs/dsh-superagent/$DSH_SUPERAGENT_TICKET"
   ```

   把个人 CLI（例如登录着你自己账号的那一份）列入禁用命令。
4. **提示词。** 填写团队小节：GitHub 的披露声明行、评审机器人、提交作者与自动合并条件。

### 管理 API

面板使用一个本地 HTTP API，智能体也可以调用它。`安装配置.md` 用它保存设置，服务脚本读取 `GET state`。

请求发往 `http://127.0.0.1:<端口>/orchestrator/api/`，并带上 `x-orchestrator-request: 1`。Host 必须是 `127.0.0.1:<端口>` 或 `localhost:<端口>`。缺少该请求头、或 `Origin` 来自其他站点，一律返回 403。

通过 API 保存拥有与面板相同的权限。与主 Session 工具发起的保存不同，它可以修改执行环境与安装用的账号字段。

智能体可以依赖下面这些路由与字段。`src/app/api.ts` 中的其余路由服务于面板，会随面板一起变化。

| 请求 | 应答 |
| --- | --- |
| `GET state` | 各页面读取的内容：`setup`，其中 `problem` 与 `feishuProblem` 各为 `null` 或一项安装问题（含 `place`、`code`、`values` 与 `detail`），以及安装解析完成后给出的 `accounts`；`health`，按部件各一条，见下表，含 `state`（`starting`、`ready`、`paused` 或 `error`）、`detail` 与 `at`；`load`，含执行器 Session 的 `running`、工单的 `queued` 与 `maxWorkers`；`paused`；以及 `masterId` |
| `GET settings` | `blocks`：`policy`、`eval` 与 `executor`，各含自身的 `value` 与 `revision`；`sources`：各来源实例，含 `id`、`kind`、`installed`、其配置块的 `value`（形如 `{"enabled": …, "config": {…}}`）与 `revision`、其种类对应的表单、以及存在时的安装 `problem`；`policyVersion`；以及 `environment`，即执行环境的 `root` 与 `variables` |
| `GET sources` | 各来源的状态：`state`（`missing`、`off`、`error`、`setup`、`starting`、`paused` 或 `ready`）、各部件的 `health`、其安装 `problem`、最近一天的 `stats`、当天被 `filtered` 的触发，以及当天被 `dropped` 的消息（最新丢弃的排在最前），每条含 `channel`、`preview`、专属工单时的 `ticket`（`id` 与 `title`）、存储中存在时的 `thread`，以及 `dropped.at` 与 `dropped.reason`（`channelGone` 或 `channelIgnored`） |
| `PUT settings/<block>` with `{"value": …, "revision": n}` | 保存一个配置块：`saved`、该块的新 `revision`、`policy_changed` 与 `restarting`。`value` 是整个配置块，形式与 `GET settings` 返回的一致；缺失的键取默认值 |
| `POST executor/pause` with `{"paused": true}` or `false` | 暂停或恢复处理：`paused` |
| `POST setup/check` | 通过重启 dsh-superagent 再跑一次安装检查：`restarting: true`。若安装检查没有需要修的问题，则拒绝执行 |
| `POST policy-sync/<source id>` | 立即同步该来源的许可名单：`policy`，即已保存的来源部分 |
| `GET prompts`, `PUT prompts` with `{"config", "baseRevision"}` | 读取提示词配置：`current`（含 `revision` 与 `config`）、`defaults`、`sections`（团队小节，按 Session 读取顺序排列）、`skillName`（团队技能名称的匹配模式）、`builtin`（团队技能不可占用的名称）与 `skillPrefix`（Session 加载技能名时所用的前缀）。或保存配置：返回新的 `revision` |
| `POST tickets/<id>/retry`, `POST tickets/<id>/stop` | 与面板一样，重试或停止一个工单 |

健康项按职责分组：

| 条目 | 报告内容 |
| --- | --- |
| `runtime` | 应用自身 |
| `models` | 等待模型预算重试的 Session |
| `evals` | 最近一小时内、之后既无判定也未被忽略的 `unavailable` 评估 |
| `assessment`, `launch`, `delivery`, `relay`, `notice`, `reply` | [003 执行](003-执行.md) 所述的已存储工作；delivery 统计等待中的工作，reply 覆盖渠道消息 |
| `worker` | 执行器 Session 的事件处理；首次失败后才出现 |
| `github`, `feishu`, `history` | 来源轮询、事件与历史补齐 |
| `sync:<source id>` | 许可名单同步 |

拒绝响应带状态码与 `error`，后者为英文文本：

- 400：取值非法（`issues`，每项带 `path`）、账号检查失败（`setup`）、固定拒绝（`code` 与 `values`），或请求体不是 JSON / 过大。
- 404：目标不存在。
- 409：修订号已过期。
- 500：其他一切情况。

各配置块：

- `source:github`、`source:feishu`：`{"enabled": true, "config": {…}}`。GitHub 的 config 含 `repository` 与 `cli`，以及默认关闭的开关 `observeIssues`、`observePulls`、`observeComments` 与 `observeCi`，用于接收仓库中每一条新 Issue、新拉取请求、新评论和默认分支的 CI；飞书的 config 含 `cli`、`chats`（形如 `[{"chatId": "oc_…", "name": "…", "listen": "mentions"}]`，也可为 `"all"`）、`directMessages`，以及取 `"none"` 或 `"mentions"` 的 `otherChats`。
- `policy`：`{"rules": […], "sources": {"github": {"allowed": [{"id": "<login>"}], "bots": [{"id": "dependabot[bot]"}]}, "feishu": {"allowed": [{"id": "ou_…", "name": "…"}], "syncChat": "oc_…", "admission": {"oc_…": {"unlistedAddressed": "explicit"}}}}}`。`bots` 列出消息可成为推断候选的机器人。一条 `admission` 行在飞书侧以群聊 id、`other` 或 `direct` 为键，在 GitHub 侧以 `issues`、`pulls`、`comments` 或 `ci` 为键；未设置的单元格取默认值（见 [002 授权](002-授权.md)）。
- `eval`：`mode`、`timeoutSeconds` 与 `model`。
- `executor`：`model`、`maxWorkers`、`directory`、`prepare` 与 `blockedCommands`。处理暂停是独立的一项设置 `paused`，由 `POST executor/pause` 修改。

修改仓库或 CLI 时，会先执行相应的安装检查。检查失败返回 400，细节在 `setup` 中。账号类修改保存成功、或在安装尚未完成时进行的任何保存，都会返回 `restarting: true`。应用重启期间，API 暂时不可用。

```sh
api=http://127.0.0.1:3082/orchestrator/api
rev=$(curl -s -H 'x-orchestrator-request: 1' $api/settings | jq '.sources[] | select(.id == "github") | .revision')
curl -s -X PUT -H 'x-orchestrator-request: 1' -H 'content-type: application/json' $api/settings/source:github \
  -d "{\"value\": {\"enabled\": true, \"config\": {\"repository\": \"acme/widgets\", \"cli\": \"$HOME/.local/bin/gh-agent\"}}, \"revision\": $rev}"
```

## 安装检查

安装检查使用 DeepSeek Harness 的子进程服务，与 worker 的 shell 一样。它会移除名称中含 KEY、PASSWORD、SECRET 或 TOKEN 的环境变量。

安装检查核验 GitHub 仓库与智能体的推送权限、写入 worker 环境，并确认 git 对 github.com 只使用智能体凭据。飞书侧检查失败只会禁用飞书来源。

安装检查写入的进程环境：

- **命令垫片** 位于 `<stateDir>/worker-bin`，排在 `PATH` 最前：`gh` 调用智能体的 CLI，`lark-cli` 调用机器人的 CLI，被禁用的命令直接失败。垫片在运行目标程序之前，会先把自己所在目录从 `PATH` 中移除。
- **git 配置** 位于 `<stateDir>/worker-gitconfig`，会取代操作者的全局与系统级 git 配置。它把智能体 CLI 指定为 github.com 的凭据助手，把 GitHub SSH 地址改写为 HTTPS，并定义 Git LFS 过滤器。HTTP 代理之类的个人 git 设置不再生效。这里不设置提交身份，git 也绝不提示输入凭据，且 `GH_TOKEN` 与 `GITHUB_TOKEN` 会被移除。

若 `worker-bin` 或 `worker-gitconfig` 中存在并非 dsh-superagent 写下的文件，安装检查会中止。若工单目录位于某个 git 仓库内、而该仓库自身的配置又添加了凭据，该工单会失败。

## 试运行

用许可名单上的 GitHub 账号，开一个 Issue 或发一条含 `@<智能体登录名> <请求内容>` 的评论。在一个轮询周期内（默认一分钟），总览应当出现一个工单。智能体会确认请求，在自己的 Session 与目录中工作，并在原会话里交付。若接入飞书，在已配置的群聊里 @ 机器人即可。

## 升级

1. 等到没有执行器正处于回合中途。
2. 备份 `<stateDir>/orchestrator.sqlite`。
3. 执行 `git pull && pnpm install && pnpm build`。
4. 执行 `scripts/dsh-superagent restart` 并检查其状态。

重启会结束运行中的派工，并以带恢复说明的新派工接替。团队文本与被覆盖的提示词部件会保留；没有覆盖的部件跟随新的默认值。升级后请复核标为 **默认值已更新** 的部件。

被较新版本迁移过的数据库，旧版本无法打开，因此回滚必须依靠升级前的备份。升级 DeepSeek Harness 本体之后，也要重启正在运行的实例，让面板加载与之匹配的构建产物。

### 智能体预设

worker 与 router 预设会在 5 秒后把 shell 命令转入后台。Session 没有对应预设就无法加载。只要这些 Session 还在使用，就要在 `cordis.patch.yml` 中保留 `dsh-superagent-worker` 与 `dsh-superagent-router` 两行；否则恢复会以 `agent-preset/not-found` 失败。

## 故障排查

安装问题会出现在总览上，附带修复入口，并使用面板当前语言；日志与 API 则显示下表所列的英文文本。

| 现象 | 原因与处理 |
| --- | --- |
| `The agent GitHub CLI is not set.` | 在 GitHub 卡片上设置智能体的 CLI |
| `The agent GitHub CLI was not found.` | 填写包装脚本的绝对路径，或 `PATH` 上可找到的命令名 |
| `The agent GitHub CLI cannot read its account` | 用 `auth login` 让包装脚本完成登录 |
| `@… cannot read …` 或 `@… cannot push to …` | 给智能体账号授予仓库写权限 |
| `The GitHub Source names no repository.` | 在 GitHub 卡片上按 `owner/name` 设置仓库 |
| 工单失败，报 `The prepare command failed: …` | 输出会指出原因，例如克隆路径写错；修好命令后重试该工单 |
| `git does not read the github.com credential configuration dsh-superagent writes` | 安装 git 2.32 或更高版本 |
| 工单失败，报 `The git configuration of the repository in … sets …` | 从该克隆的 `.git/config` 里删去所指的凭据或 `http.*.extraheader` 设置 |
| `… was not written by dsh-superagent` | 把所指文件移出 `<stateDir>/worker-bin` 或 `<stateDir>/worker-gitconfig`，或改用别的 `stateDir` |
| `The bot lark-cli allows user identities` | 把飞书来源指向仅限机器人身份的配置，做法见上文「飞书机器人」 |
| `The bot lark-cli does not work.` 或 `The bot identity of app … is …` | 核对配置中的 app id 与密钥 |
| `The Feishu bot is not a member of the chat.` | 在群设置里把机器人加进群聊；下一次尝试即可成功 |
| `status` 以 2 退出 | 某个部件报错，重启无法修复：`errors` 会按「管理 API」一节列出每个部件及其细节；部件恢复正常后会自行清除对应条目 |
| `status` 以 3 退出 | 安装检查在等待：`setup` 说明缺什么，总览链向能修复它的设置 |
| `status` 以 1 退出 | 服务未运行、运行了两份、无响应，或运行时报错；具体是哪一种，输出与最新日志会说明 |
| `… timed out after 90 s`、`… was stopped by …`、`… exited with code …` 或 `… could not run: …` | 某个 CLI 失败却没打印原因；以操作者用户身份手动运行所指程序，看它自己报什么 |
| 面板提示 dsh-superagent 无响应 | 它正在重启，或因配置问题没能启动；DeepSeek Harness 日志会指出原因 |
| （日志）`dsh-superagent configuration has keys it does not use` | 删去所指的键；该消息会说明每个值现在归到哪里 |
| 日志提示插件与当前 dsh 不兼容 | 安装落在 `engines.dsh` 区间内的 DeepSeek Harness 版本 |
| 升级 DeepSeek Harness 后面板显示 "Failed to load plugins" | 重启正在运行的实例 |
| @ 之后没有任何反应 | 确认发言者在该来源的许可名单上、来源已开启、处理未被暂停。在 GitHub 上，通过编辑 Issue 正文补上的 @ 不会被收到；请在评论里 @ 智能体 |
