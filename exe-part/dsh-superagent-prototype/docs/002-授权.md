# 002 授权

授权决定谁可以发起工作，以及这项工作可以包含什么。本文建立在 [001 领域模型](001-领域模型.md) 之上。

许可名单、规则与授权（Mandate）由宿主强制执行。消息、评论与被援引的文档只是决策的输入，无法改动这些权限。

## 触发的两条路径

### 评估：决定是否开工

来源会记录消息是否点名了智能体：`mention` 表示提及机器人或智能体账号，`direct` 表示私信。准入（Gate）据此检查发送者与该来源的策略：

- 许可之人点名智能体，构成明确请求。
- 某人在已有工单的线程上追问，遵循下述规则。
- 其他人工消息按其接收范围查准入表。
- 来源的机器人名单上的机器人只能产生推断候选，绝不能构成明确请求；其他机器人一律不予准入。

### 订阅：延续既有工作

已订阅线程上的每条消息都会作为上下文送达订阅它的工单，包括来自机器人与 CI 的消息。这种投递绕过准入，也不授予任何新的权限；每个工单仍受其授权约束。

工单自身线程上的人的消息，归该工单的执行器裁决。主 Session 把某条消息挂到工单上时同样如此。消息归执行器所有期间，不进入评估，也不产生决定；每个执行器要么在其工单范围内处理该请求，要么把它交回，以便路由到别处。

只要工单仍然活跃，这种归属就持续存在，即便有人取消了它的订阅。它同样覆盖未被人工停止、且有消息正等着唤醒它的已结束工单。

主 Session 会收到一条追问通知。消息归执行器所有期间，主 Session 只能按人的请求停止工作；接单、挂载、忽略与重新入队都会被拒绝。停止仍需经过准入，并采用下文所述的追问强度。

### 交回消息与释放追问

当消息请求的工作超出工单范围、或本属于另一个工单时，执行器把它交回一次。工单保留自己的订阅。若所挂线程与工作无关，执行器会把它在该线程上持有的消息一并交回。

只有在没有任何工单仍持有该消息之后，它才会进入一次全新的评估。其候选卡会带上各执行器给出的理由。准入按该线程上的普通消息来判定它，主 Session 可以接单、把它挂到别处或忽略。交回一条本不属于该工单的消息（例如机器人消息，或某人已送交评估的消息）不会触发任何入队。

工单结束时，会释放其执行器未读或未接手的追问。其中包括从未送达执行器的消息，以及在其最后一次报告或回合结束之后才送达、且执行器既未确认、未答复、也未交回的消息。每条被释放的消息在没有其他工单持有时进入评估。一次停止只结束被停那个工单的工作。

除非另一个工单把停止消息交回，已停止的工单不会把自己的停止消息再次送交评估；执行停止的那个主 Session 可以把该消息的其余部分作为新工作接单。

人也可以从面板把一条已被持有的追问送交评估。若主 Session 随后把它重新挂到某个活跃工单，执行器会再次收到它。当没有任何有效判定覆盖该消息时，面板还会提供「重新评估」入口。

### 仅作上下文的订阅

执行器可以关注一个相关线程（例如另一个 Issue 或拉取请求）以获取上下文。那里的消息会送达工单，但不授予权限，也不带追问强度。此类线程上的人工消息不会唤醒已结束的工单，除非主 Session 把该线程上的某条消息挂载过去。主 Session 关于其他工作的备注同样只作上下文。

没有送达任何工单的人工消息——包括所属工单已被人工停止的线程上的消息——走评估路径。机器人消息则无论是否已被投递给订阅工单，都会走该路径。

## 强度

| 强度 | 情形 |
| --- | --- |
| 明确 | 名单上的人点名智能体，或在已有工单的线程上追问；准入表中被设为「明确请求」的单元格 |
| 推断 | 名单外的人在已有工单的线程上追问，除非其在准入表中的单元格为「明确」；准入表中被设为「推断候选」的单元格；来源机器人名单上的机器人所发的、点名智能体或出现在来源接收全部消息范围内的消息 |
| 不予准入 | 其他任何机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的所有推断情形 |

对名单外的人，准入表中的「明确」单元格具有优先权，即便在已有工单的线程上也是如此，并且在所有接单模式下都生效。否则其追问属于推断，在 `off` 模式下不予准入。仅被关注作上下文的线程上的消息，采用准入表而非追问强度来判定。

## 准入

每个来源的策略都有一张准入表，其行是接收范围：

- **飞书：** 每个已配置的群聊、机器人收到 @ 提及的其他群聊，以及私聊。只有在飞书卡片上把 **其他群** 设为 **仅 @** 时，才会接收其他群聊。
- **GitHub：** 新建 Issue、新建拉取请求、评论，以及默认分支的 CI。

一行最多三个单元格。每个单元格决定一条消息是成为明确请求、推断候选，还是什么都不是：

| 单元格 | 可选值 | 默认值 |
| --- | --- | --- |
| 在名单上、未点名智能体 | 推断、忽略 | 推断 |
| 不在名单上、点名智能体 | 明确、推断、忽略 | 忽略 |
| 不在名单上、未点名智能体 | 推断、忽略 | 忽略 |

针对未点名消息的单元格，仅在来源接收全部消息的位置可用，例如设为 **全部消息** 的飞书群聊，或开启了「接收全部」开关的 GitHub 范围。CI 结果没有发送者，因此该行只提供最后一个单元格。机器人消息改用机器人名单，而不走这些单元格。

把「名单外且已点名」单元格设为「明确」，等于允许该范围内的任何人通过 @ 智能体来分派工作，这对专门的支持群聊很有用。推断候选仍取决于接单模式。追问通常绕过此表，但「明确」单元格仍会赋予明确强度。

准入表属于策略版本的一部分。放宽某个单元格不会立刻停止按它接单的活跃工单；但在恢复前重新校验时，它可能撤销这些工单的授权。

### 机器人与自动化审阅者

宿主把 GitHub App、以 `[bot]` 结尾的登录名以及飞书机器人识别为机器人。来源可以列出若干机器人（例如 `dependabot[bot]`），允许它们的消息成为推断候选。这些消息必须点名智能体，或发布在接收全部消息的范围内。它们不能构成明确请求，也不能停止工单。

使用普通账号的自动化审阅者，在宿主看来算作人。其评论会送达已订阅的工单并生成追问通知。团队必须在提示词文本中把这类账号标明为自动化审阅者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接单、挂载、停止或忽略决定。每一项独立处理：某项被拒或字段缺失，不影响其他项执行。

推断候选通常需要一次完整研判。捷径只有一条：若候选卡明显不涉及任何已启用的规则（例如闲聊或无关讨论），主 Session 可以直接忽略。此时决定会记录 `ignoredFromCard`，以区别于经过规则研判的情形。主 Session 从其提示词的策略小节读取已启用的规则。

接单一个推断候选始终需要研判。直接接单会拒绝准入未判定为「明确」的触发。

## 接单模式与规则

接单模式属于策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断都不会成为候选，例如未点名的消息、机器人消息，或名单外之人的追问 |
| `observe`（默认） | 推断候选仍被研判；正面研判记录为标记为「本会接单」的忽略，不实际接单 |
| `auto` | 对推断候选的正面研判直接接单 |

明确请求在所有模式下都有效。先从 `observe` 起步，检视记录下来的决定后再切到 `auto`。每次研判对每条已启用的规则恰好判定一次，无论是否命中。主动接单至少需要命中一条规则。

每条规则描述一类主动工作。工单的授权会记录命中的规则，其执行器会收到这些规则的名称与指令。

对该工单而言，规则中的流程与沟通要求优先于默认要求：静默规则可以免掉一次确认；评审规则可以指定必需的审阅者以及合并前的批准。适用于所有工单的要求，应写进团队提示词小节。

## 策略版本

规则、接单模式以及每个来源的策略共同构成策略版本。每个授权都记录下接单时所依据的版本。

版本变更会丢弃正在运行的评估，并把它持有的触发重新入队；同时向每个受影响的活跃工单发送一条「策略已变更」的输入。该输入说明属于下列哪种情况：

- 命中的规则发生变化（附上新文本），或已不再适用；
- 请求人可能不再具备发起工作的资格；或
- 主动工作不再被接单，例如模式由 `auto` 改成了别的值。

未受影响的工单不会收到通知。变更也不会立即撤销活跃工单的授权。

来源配置与策略彼此独立：前者控制什么能进入系统——读取哪些群聊、某个范围是接收全部消息还是只接收 @ 提及。授权会记录其来源与接收范围。恢复工作要求来源仍在监听该线程，但不要求它仍接收该线程上的全部消息。

回复在其来源关闭期间会等待；若来源不再监听目标位置，回复会被丢弃。

对执行器「可以拿自己的结果做什么」的约束（例如何时可以合并）并不决定谁有权授权工作。它属于智能体的指令，而非策略。

## 恢复与停止

已结束的工单保留其授权。其自身线程上的人的消息可以直接恢复同一项工作，无需新的评估或决定，且与发送者是谁无关。机器人与 CI 不会唤醒已结束的工单。执行器判断请求是否落在范围内；若不在，就结束本轮。

只有三种操作会改变授权：接单创建它、人工停止撤回它、重新校验失败撤销它。被人工停止的工单保持结束状态，不再接收任何内容；在那里请求的工作需要一次新的接单。

### 恢复前的重新校验

来源必须仍在监听原线程。其余检查取决于授权的依据：

- 基于明确追问的授权直接通过。
- 推断型授权需要 `auto` 模式，且命中的规则仍处于启用状态。
- 由准入表单元格准入的授权，在当天的表格与发送者名单成员关系下，仍须至少获得原有强度。因此把某位发送者移出名单，可能撤销经「名单内发送者」单元格接单的授权。
- 机器人型授权要求该机器人仍在来源的机器人名单上。准入表推断型与机器人型授权同样需要 `auto` 模式及仍处于启用状态的命中规则。
- 其他授权要求发送者仍在来源的许可名单上。

若重新校验失败，工单保持结束状态，且不接收任何等待中的消息。每条消息都被视为未送达任何工单；若无其他工单持有它，就进入评估。主 Session 不会被告知它曾送达执行器。处理暂停之后同样如此。向该工单挂载会被拒绝，后续工作需要一次新的接单。

- **人在线程里说「停止」只是一条普通触发**，由评估决定是否停止；执行器不得声称有人要求它停止。
- **面板上的「停止」是一条命令**，直接作用于工单，并记录为人工停止。
- **等待条件归来源负责。** 像「N 小时仍无负责人」这样的条件，应由一个自行等待并复查的来源实现；评估从不等待。

## 评估未能完成时

时限从候选送达主 Session 时开始计算。等待投递所花的时间不计入，未送达的候选永不过期。

超时的评估会把它持有的触发重新入队再试一次。连续两次重试后，第三次超时记录为 `unavailable`。研判失败同样记录为 `unavailable`；后续触发可以开启一次新的评估。若发生策略变更，或依据过期策略作出了决定，则记录 `unavailable` 并立即按当前版本把该批次重新入队。

`evals` 健康项报告最近一小时内未解决的 `unavailable` 决定。`scripts/dsh-superagent status` 会包含该错误。

只有当 `unavailable` 决定距今不足 24 小时、仍是所在线程上的最后一条决定、尚未被忽略、且该线程既未排队也不在评估中时，面板才会请求人工关注。人可以重新评估该触发，或忽略该问题。
