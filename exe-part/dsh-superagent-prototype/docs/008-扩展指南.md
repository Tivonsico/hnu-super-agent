# 008 扩展指南

本指南演示如何扩展 dsh-superagent。它使用 [001 领域模型](001-领域模型.md) 与 [002 授权](002-授权.md) 中的术语，以及 [007 架构](007-架构.md) 中的组件。

## 新增一个来源

本例实现一个名为 `webhook` 的来源种类。它通过一个虚构的 CLI `hookq` 读取假想的消息队列，并把消息转换成触发。其余接口都属于 dsh-superagent 已有部分。

实现有四项职责：翻译事件、定义接收与授权规则、提供回复与上下文、维持一个轮询循环。下面按编号依次搭出这些部分。

本例假定 CLI 的契约如下：

- `hookq pull --after <n> --json` 打印位置 `n` 之后的消息，旧的在前：`{"me": "<智能体在队列上的 id>", "items": […], "next": <位置>}`。每个条目含 `id`、`conversation`、`thread`（发起该线程的消息 id；那条发起消息上没有此字段）、带 `id` 与 `bot` 的 `sender`，以及 `mentions_me`、`text`、`at` 与 `url`。
- `hookq reply --conversation <id> --to <message id> --key <key> --text <text>` 在某条消息下回复，同一个 key 只回复一次。若会话已被删除，它会失败，并在标准错误输出 `{"error": {"code": 410, "message": "…"}}`。
- `hookq thread --conversation <id> --root <message id> --json`（翻到后续页时加 `--after <cursor>`）打印线程的一页，旧的在前：`{"items": […], "next": "<cursor>"}`；最后一页没有 `next`。

把该 kind 及其插件入口放进 `src/sources/webhook.ts`，照 `src/sources/github.ts` 的写法来。若来源规模变大，就像飞书来源那样，把翻译、渠道与轮询代码拆成独立模块。

### 1. 把事件映射到领域

写代码之前先定下稳定的映射。触发 id、线程 id 与渠道地址都会持久化，日后改动可能让已有记录失去关联。

| 概念 | webhook 队列中的对应物 |
| --- | --- |
| 触发 | 一条消息 |
| 线程 | 一个会话里的一条消息及其回复：`<conversation>:<首条消息的 id>` |
| 发起者 | 发送者在队列上的 id，与许可名单所用的写法一致 |
| 渠道地址 | 会话，以及回复所挂在的那条消息 |
| 接收范围 | 一个会话，在准入表里有自己的一行 |

- `kind` 是稳定的来源 id。它出现在触发的 `source`、线程键前缀、`source:webhook` 设置块以及来源策略中。
- `schema` 校验已存储的配置并提供默认值。在操作者保存某个实例之前，注册表会用这些默认值创建一个已启用的实例。请让默认值不接收任何内容；本例默认不配置任何会话。
- `fields` 无需定制面板代码即可生成来源设置表单。`rows` 字段以第一列为键编辑条目；`advanced` 把不常用的设置收起来。若来源能把 id 解析成显示名称，就实现 `refreshLabels`，并把名称保存在 `KV.sources.labels(kind)` 下；带 `choose` 与 `refresh` 的列随后即可提供这些名称。
- 可选的 `facts(deployment)` 用于展示由安装检查推导出的值，例如某个 CLI 背后的账号。安装检查目前只检查 `SETUP_FIELDS` 中列出的 GitHub 与飞书字段，因此本例不提供 facts。
- `health` 声明来源的健康项，初始为 `starting`。注册时会认领每个名称，并拒绝与 `runtime`、`reply`、`worker` 或各类副作用同名。请使用 kind 自己的名称，并把 `sync:<id>` 留给策略同步。健康项一旦为 `error`，状态脚本就会以 2 退出、每小时巡检也会通知操作者，因此只在可能需要人工介入时才报 `error`。

### 3. 把消息翻译成触发

转换之前先校验 CLI 的响应：

```ts
/** `hookq pull` 与 `hookq thread` 输出的一条消息。 */
const MessageSchema = z.looseObject({
  id: z.string().min(1), conversation: z.string().min(1), thread: z.string().optional(),
  sender: z.looseObject({ id: z.string(), bot: z.boolean().default(false) }), mentions_me: z.boolean().default(false),
  text: z.string(), at: z.string(), url: z.string().optional(),
})
type QueueMessage = z.infer<typeof MessageSchema>
/** `hookq pull`（其 items 逐条读取）与 `hookq thread` 的应答。 */
const PageSchema = z.looseObject({ me: z.string(), items: z.array(z.unknown()), next: z.number().int() })
const ThreadPageSchema = z.looseObject({ items: z.array(MessageSchema), next: z.string().optional() })
```

```ts
/** 一条队列消息对应的触发；智能体自己的消息不产生触发。 */
export function webhookTrigger(message: QueueMessage, me: string): Trigger | undefined {
  if (message.sender.id === me) return undefined
  const thread = `${message.conversation}:${message.thread ?? message.id}`
  return {
    id: key('webhook', message.id),
    source: 'webhook',
    threads: [{ source: 'webhook', id: thread }],
    actor: { source: 'webhook', id: message.sender.id },
    human: !message.sender.bot,
    ...(message.mentions_me ? { addressed: 'mention' as const } : {}),
    at: message.at,
    text: message.text,
    channel: { source: 'webhook', thread: `webhook:${thread}`,
      address: { conversation: message.conversation, message: message.id, ...(message.url ? { url: message.url } : {}) } },
    ...(message.url ? { url: message.url } : {}),
    meta: { conversation: message.conversation, messageId: message.id, root: message.thread ?? message.id },
  }
}
```

- **稳定的 id。** 用 `key` 从队列 id 推导触发 id。`Engine.receive` 对已存储的 id 返回 `duplicate`，而重复接单只会创建一个工单，因此重读消息是安全的。若要把编辑视作新事件，就在 id 里带上编辑版本，GitHub 对评论的 `updated_at` 正是这么做的。
- **线程。** 第一个线程是主线程，持有该评估；其余线程补充关联上下文。id 由来源自行选定，完整键为 `webhook:<id>`。
- **发送者。** `actor` 中使用来源原生的 id。机器人与 CI 设为 `human: false`。名单内的机器人只能成为推断候选。像 CI 那样空的 actor id，会走「名单外、未点名」对应的准入单元格。只有消息确实点名智能体时，才把 `addressed` 设为 `mention` 或 `direct`；这会让许可之人的消息获得明确强度。绝不为智能体自己的消息生成触发。
- **回复目标与元数据。** `channel` 指明回复发往何处，`url` 链向来源消息。`channel.thread` 把消息分组以便按序投递：同一工单的后续消息要等更早的那些发出，直到更早那条连续失败三次。其他工单不受牵连。来源专属字段放在 `meta` 里，例如接收会话与线程根消息。`meta` 与 `text` 都是不可信数据，不构成授权。

智能体可以通过 `orchestrator_read trigger/<id>` 与 `thread/<key>` 读取新 kind。它们暴露消息文本、去向与邻近触发。新 kind 不会自动获得内置技能、原始服务记录的读取资源或拉取请求绑定。

全文搜索无需额外代码即可工作。当人会用来源专属的引用（例如消息 id、URL 或 `#12`）时，实现 `find(query)`，返回这些引用所指向的线程键与搜索词：

```ts
  find: query => ({ threads: [], terms: [...new Set(query.match(/\bm[0-9]+\b/g) ?? [])] }),
```

此处把查询里出现的队列消息 id（例如 `m42`）拿来搜索对应触发。

### 4. 来源接收什么：范围

```ts
  scope({ meta }, config) {
    const conversation = config.conversations.find(item => item.id === meta.conversation)
    if (!conversation) return { listened: false, reason: 'conversation_not_listed' }
    return { listened: true, observed: conversation.listen === 'all', row: conversation.id }
  },
```

引擎对每条到达的触发，都会经 `SourceRegistry` 调用 `scope`。范围之外的消息会连同原因存成 `filtered`，且不创建线程。请把消息交给 `receive`，而不是在轮询循环里悄悄丢掉，这样面板才能解释过滤原因。

`observed: true` 表示来源在该范围内接收未点名消息，从而允许准入表对它们作出判定；`row` 指出对应的准入表行。

重新校验会用授权中保存的元数据调用 `scope`，因此它只能依赖 `meta` 与配置。恢复要求 `listened`，不要求 `observed`。没有 `scope` 时，一个 kind 会接收自己产生的每一条触发，但不「观察」任何一条。

### 5. 回复：渠道

```ts
  channel: {
    allowed: (address, config) => config.conversations.some(item => item.id === address.conversation),
    send: sendWebhook,
    link: address => ({ url: address.url ?? '',
      label: { zh: `Webhook 对话 ${address.conversation}`, en: `Webhook conversation ${address.conversation}` } }),
  },
```

```ts
export async function sendWebhook(host: Pick<SourceContext, 'commands'>, message: OutboundMessage): Promise<'sent' | 'gone'> {
  const { conversation, message: to } = message.channel.address
  if (!conversation || !to) throw new Error('Missing webhook reply target')
  try {
    await host.commands.run('hookq', ['reply', '--conversation', conversation, '--to', to, '--key', message.id,
      '--text', message.text])
    return 'sent'
  } catch (error) {
    if (error instanceof CliError && error.code === 410) return 'gone'
    throw error
  }
}
```

- **幂等发送。** Outbox 调用 `SourceRegistry.send`，后者调用 `channel.send`。来源插件未加载时，消息会等待。一次发送可能在远端已收到之后才失败，因此重试不能造成重复消息。用 `message.id` 作幂等键：`hookq` 支持 `--key`，GitHub 存一个隐藏的评论标记，飞书接受幂等键。
- **永久失败与可重试失败。** 成功返回 `sent`；只有投递永久不可能时（例如本例的 410）才返回 `gone`。`gone` 的消息保留为「已丢弃」且不再入队，并出现在 `GET sources` 与来源页上。其他失败一律抛出，让 Outbox 从 5 秒起按翻倍退避重试，最长 300 秒。`CliError.code` 取自 CLI 输出所报告的代码。
- **允许的目标。** `allowed(address, config)` 只检查已保存的地址与当前配置，因此把所需事实都放进地址；例如飞书会记录该群聊是否为私聊。不再被监听的目标会被丢弃，而来源被禁用时消息只是等待。没有 `allowed` 时，来源启用期间所有地址都被允许。
- **链接。** `link(address, links)` 返回面板经 `SourceRegistry.link` 展示的 URL 与标签。

### 6. 供研判使用的线程上下文

```ts
  threadContext: {
    messageId: trigger => String(trigger.meta.messageId ?? ''),
    // 队列线程是平铺的：根消息以及被回复的那条消息都在第一页，GitHub 也如此。
    read: async (commands, trigger, _part, cursor) => {
      const page = ThreadPageSchema.parse(JSON.parse(await commands.run('hookq', ['thread', '--conversation',
        String(trigger.meta.conversation), '--root', String(trigger.meta.root), '--json', ...(cursor ? ['--after', cursor] : [])])))
      const messages = page.items.map(item => ({ id: item.id, from: item.sender.id, at: item.at, text: item.text,
        ...(item.sender.bot ? { bot: true as const } : {}), ...(item.url ? { url: item.url } : {}) }))
      return { messages, ...(page.next ? { next: page.next } : {}), body: { messages } }
    },
  },
```

主动研判需要触发周围的会话。`orchestrator_eval` 读取初始窗口，`orchestrator_eval_read` 展开后续页、根消息或父消息。实现可选的 `threadContext` 接口来提供这些读取：

- `read(commands, trigger, part, cursor, config)` 返回一个 `ContextPart`。其 `messages` 采用 `ContextMessage`：`{id, from, at, text}`，外加适用的 `bot`、`deleted`、`reply_to`、`url`、`path` 与 `line` 字段。最后一页省略 `next`。`body` 是展示给研判 Session 的内容，这里就是同一批消息。可选的 `status` 用于描述特殊结果，例如飞书的 `chat_neighbours`。`part` 取 `thread`、`root` 或 `parent`。
- `messageId(trigger)` 在其中定位该触发自己的消息。
- `images(text)` 与 `image(…)` 供消息携带图片的 kind 使用（飞书就是如此）；本例省略它们。

没有 `threadContext` 的 kind 不给研判提供任何线程上下文；触发自身的文本仍然可读。

若消息会回复更早的消息，就补上 `repliesTo(trigger)`。它返回对应的触发 id，使追问通知与 worker 输入在已存储时能够显示被回复的那条消息。例如，若 `hookq` 提供 `reply_to`，而翻译阶段把它存为 `meta.replyTo`：

```ts
  repliesTo: trigger => typeof trigger.meta.replyTo === 'string' ? key('webhook', trigger.meta.replyTo) : undefined,
```

### 7. 谁可以提出请求：来源在策略中的那一部分

```ts
  policy: {
    schema: z.object({ allowed: z.array(z.object({ id: z.string().min(1), name: z.string().trim().max(100).optional() }).strict())
      .default([]) }).strict(),
    fields: [{ key: 'allowed', type: 'rows', label: { zh: '能发起工作的发送者', en: 'Senders who may originate work' }, columns: [
      { key: 'id', type: 'text', label: { zh: '发送者', en: 'Sender' } },
      { key: 'name', type: 'text', label: { zh: '名字', en: 'Name' }, optional: true }] }],
    explicit: { zh: '名单里的人在消息里 @ 智能体。', en: 'Someone on the list mentions the agent in a message.' },
    rows: stored => ConfigSchema.parse(stored).conversations.map(conversation => {
      const all = conversation.listen === 'all'
      return { id: conversation.id, label: conversation.id, note: all ? { zh: '全部消息', en: 'All' } : { zh: '仅 @', en: '@ only' },
        cells: { listedUnaddressed: all, unlistedAddressed: true, unlistedUnaddressed: all } }
    }),
  },
```

- `schema` 校验来源策略，包括 `allowed` 中的发送者 id。id 比较不区分大小写。准入表单独校验，并在各 kind 之间共用。这部分策略保存在 `policy.sources.webhook`，并计入策略版本。
- `fields` 生成 **评估 → 各来源分别设置** 下的表单，以 `allowed` 开头。`explicit` 说明怎样才算点名智能体。可选的 `unnamed: {person, bot}` 为飞书 `ou_…` 这类不可读 id 提供显示标签；本例省略它，因为队列 id 本身是可读名称。
- `rows(config)` 列出准入范围及其可用单元格。每行的 id 必须与 `scope` 返回的 `row` 一致。针对未点名消息的单元格，仅在来源「观察」这些消息的范围内可用。没有 `rows` 的 kind 使用默认单元格。
- 可选的 `bots` 列出有资格成为推断候选的机器人，条目形状与 `allowed` 相同。没有它，任何机器人都不予准入。
- 可选的 `sync: {label, ready(part), run(host, part, signal)}` 在启动时以及点击 **立即同步** 时刷新成员名单，飞书用的是群成员。失败显示在 `sync:<id>` 下，并从一分钟起按翻倍退避重试、最长一小时，直到成功。

### 8. 给执行器的变量

```ts
  environment: {
    variables: [{ key: 'DSH_SUPERAGENT_WEBHOOK_CONVERSATION', description: {
      zh: '接下工单的 webhook 对话；工单不是从这个来源来的时为空',
      en: 'The webhook conversation that started the ticket; empty when the ticket did not start on this Source' } }],
    values: ({ trigger }) => ({
      DSH_SUPERAGENT_WEBHOOK_CONVERSATION: trigger?.source === 'webhook' ? String(trigger.meta.conversation ?? '') : '' }),
  },
```

即使来源被禁用，执行设置也会在准备命令旁展示已声明的 `variables`。启用期间，`values` 依据部署、配置与最初的触发，给出该工单专属的取值。

准备命令读取环境变量，worker 在自己的指令里读取它们的值。请使用 `DSH_SUPERAGENT_<KIND>_…` 前缀；对来自其他来源的工单返回空值；绝不包含凭据。

### 9. 插件入口及其循环

```ts
export const name = 'dsh-superagent-webhook'
export const inject = ['orchestrator']
export function apply(ctx: Context): void {
  ctx.effect(() => ctx.orchestrator.sources.register(webhookKind), 'webhook: source kind')
  ctx.effect(() => {
    const source = sourceContext(ctx.orchestrator, webhookKind)
    const controller = new AbortController()
    // DSH 遇到未处理的 rejection 会结束进程，因此逃出循环的失败要转成来源的健康状态。
    const running = watch(source, controller.signal)
      .catch((error: unknown) => { source.report('webhook', { state: 'error', detail: String(error) }) })
    return async () => { controller.abort(); await running }
  })
}
```

插件注入 `orchestrator`。第一个 effect 注册该 kind，并在释放时注销；第二个用 `SourceContext` 运行轮询循环。释放时会中止循环并等待它结束，应用停止或重启时同样如此。

```ts
async function watch(ctx: SourceContext, signal: AbortSignal): Promise<void> {
  await ctx.ready
  // 安装检查解析出账号后会重启一次 dsh-superagent；在此之前来源不读取任何内容。
  if (!ctx.configured()) { ctx.report('webhook', health('paused', 'setupPending')); return }
  let failures = 0
  while (!signal.aborted) {
    const config = ctx.config<WebhookConfig>('webhook')
    if (!config) ctx.report('webhook', health('paused', 'sourceOff'))
    else {
      const at = new Date().toISOString()
      try {
        const { read, unreadable } = await pollQueue(ctx, signal)
        failures = 0
        ctx.report('webhook', { state: 'ready', detail: `${read} messages, ${unreadable} unreadable`, at })
      } catch (error) {
        failures += 1
        // 一次网络故障留到下一轮重试；连续三次就需要人工介入。
        if (!signal.aborted && failures >= 3) {
          ctx.report('webhook', health('error', 'pollFailures', { count: String(failures), error: String(error) }))
        }
      }
    }
    await delay((config?.pollSeconds ?? 30) * 1000, undefined, { signal }).catch(() => {})
  }
}

/** 读取游标之后的队列，逐条接收消息，再把游标推过它们。 */
export async function pollQueue(ctx: SourceContext, signal: AbortSignal): Promise<{ read: number; unreadable: number }> {
  const after = ctx.state.get(KV.webhook.cursor) ?? 0
  const output = await ctx.commands.withSignal(signal).run('hookq', ['pull', '--after', String(after), '--json'])
  const page = PageSchema.parse(JSON.parse(output))
  let unreadable = 0
  for (const item of page.items) {
    if (signal.aborted) throw new Error('The webhook Source stopped during the read')
    const message = MessageSchema.safeParse(item)
    if (!message.success) { unreadable++; continue }
    const trigger = webhookTrigger(message.data, page.me)
    if (!trigger) continue
    await ctx.receive(trigger)
    const conversation = { label: { zh: '对话', en: 'Conversation' }, value: message.data.conversation }
    for (const ref of trigger.threads) ctx.threads.describe(threadKey(ref), { facts: { conversation } })
  }
  ctx.state.set(KV.webhook.cursor, page.next)
  return { read: page.items.length, unreadable }
}
```

- **安装检查与开关。** 等待 `ctx.ready`；`ctx.configured()` 为 false 时不读取任何内容。每轮都重新读取 `ctx.config(kind)`：来源关闭时它是 `undefined`。
- **游标。** 用 `KV`（`src/kv.ts`）中的带类型条目把读取位置存在 `ctx.state` 里，例如 `webhook: {cursor: record<number>('webhook-cursor')}`。`tests/store.spec.ts` 要求键的字面量只出现在那张登记表中。外部包可以用导出的 `record` 与 `family` 定义键。设为 `undefined` 即删除一条记录；`ctx.atomic` 把多次写入合成一个事务。

  只有在游标所覆盖的每条触发都存好之后，才推进游标。被中断的一轮会保持游标不动；稳定的 id 让重放是安全的。对于时间戳游标，`src/sources/poll.ts` 的 `cursorAt(started)` 会回退五秒，以容纳远端迟到的写入。
- **线程元数据。** 接收一条触发之后，调用 `ctx.threads.describe(key, {label, url, facts})` 填好它的展示信息。`ctx.threads.patch(key, meta)` 委托给 `threads.patchMeta`，用于设置归来源所有的键，或在值为 `undefined` 时移除它们。两者都会忽略不存在的线程，包括被过滤触发所对应的线程。
- **逐条错误处理。** 统计格式不合法的条目并继续，不要让整批失败。`src/infra/commands.ts` 的 `validItems(item, list, tally)` 正支持这种做法。对各自独立轮询的线程，使用 `src/sources/poll.ts` 的 `pollThreads`，它会把每次失败记为 `pollError`；其 `polled` 谓词保留活跃订阅，以及从「最后一条触发」与「工单结束」中较晚者起算的两周窗口。
- **健康状态。** 只通过 `ctx.report` 写已声明的条目。`health(state, code, values)` 提供 `setupPending`、`sourceOff`、`pollFailures` 这类固定文案。先累计连续失败次数，再报 `error`。
- **中止。** 把 signal 传给 `ctx.commands.withSignal(signal)` 与 `delay`，并在逐条处理之间检查它，这样停止或重启能立刻结束循环。

本例不发送由来源主动发出的通知。需要这类通知的来源可调用 `ctx.notify`；Outbox 会像处理其他回复一样投递它们。

本例也不把线程绑定到工单完成上。只有当来源自身的线程生命周期决定工作是否完成（GitHub 拉取请求正是如此）时，才使用 `ctx.tickets.bindThread` 与 `threadClosed`。工单何时结束，仍由引擎决定。

```ts
function queue(h: ReturnType<typeof host>, answer: () => unknown) {

```

`message(id, fields)` 用于构造队列条目。至少覆盖以下情形：

- 翻译：稳定的 id、线程、发起者、`human` 与 `addressed`，以及智能体自己的消息不产生触发；
- 一轮轮询：触发只存一次、范围外的一条被 `filtered`、游标在它们之后推进、许可之人的 @ 被判定为 `explicit`；
- 被中途打断的一轮，游标保持不变；
- `send`：成功返回 `sent`、仅 410 返回 `gone`、其他失败一律抛出，CLI 的错误用 `commandError` 构造；
- 线程上下文：一页的消息与下一页的游标，参照 `tests/registry.spec.ts` 经 `SourceRegistry.threadContext` 读取某个 kind 线程的做法；
- 插件：`apply` 注册该 kind、在安装检查等待期间上报 `setupPending`、其释放函数注销该 kind，以及逃出循环的失败变成来源健康状态而不是未处理的 rejection；
- 来源在策略中的那一部分及其准入行，参照 `tests/registry.spec.ts` 与 `tests/policy.spec.ts` 检验飞书来源的做法。
