# 003 执行

本文沿着一个已接单的工单，走完执行、交付与恢复。它建立在 [001 领域模型](001-领域模型.md) 与 [002 授权](002-授权.md) 之上。

## 工单阶段

每个开启中的工单有一个阶段，由它正在等待什么决定。请自上而下读表，第一个匹配的行生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；2 秒后重试，随后按翻倍延迟重试、最长至一分钟；投递成功、产生新派工或工单结束都会清除该状态 | 输入未送达 |
| person / answer | 工单上存在待人工决定 | 等待答复 |
| person / review | 最新报告为 `ready` | 等待评审 |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，且此后没有人的消息送达该工单 | 受阻 · 失败 |
| working / queued | 尚无派工，或派工处于待启动 | 排队中 |
| idle | 最新报告为 `waiting`，或派工已结束 | 等待触发 |
| working | 其余情形 | 执行中 |

`person` 阶段表示没有人工输入，工单就无法继续。新的人工消息会把 `blocked` 或 `failed` 工单交回执行器，因此它会移到下一个匹配阶段，通常是 `working`。

`idle` 工单已结束本轮，且没有悬而未决的问题。已订阅线程上的一条触发可以让它继续。

## 执行器

每个工单获得一个名为 `worker-<工单 id>` 的执行器 Session，以及一个以工简短名命名的目录。目录创建在配置的执行根目录下，默认为 `<stateDir>/work`。

执行器 Session 以操作者的操作系统用户身份执行命令，无需逐条批准。其 `dsh-superagent-worker` 预设包含工作所需工具，并把前台 shell 命令在 5 秒后转为后台作业。这样 worker 能在下一步就收到新消息，而不必等一条长命令跑完。

主 Session 使用 `dsh-superagent-router`，同样有 5 秒的 shell 与作业等待上限，但工具集更小，仅用于路由。Session 会保留创建时选定的预设。worker 的子智能体使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与 worker 槽位

若一个回合结束时仍有 shell 作业或子智能体在运行，工单保留自己的 worker 槽位并保持执行中状态。它不会被报告为等待，主 Session 也不会收到等待报告。某个作业或子智能体完成后，会带着结果在同一槽位唤醒执行器。一旦某回合结束时没有后台工作，执行器就按常规报告等待。

每个回合结束后，后台工作最多还有 30 分钟完成。到达上限时，shell 作业被终止，工单被报告为等待。报告中包含执行器最后的输出，以及哪些作业被终止、哪些子智能体仍在运行。子智能体可以继续执行。执行器会在下一回合读取被终止作业的结果。

交接给人会立即释放槽位，并让该报告继续生效。这适用于 `ready` 报告或一次提问之后（除非此后又到了别的输入），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时子智能体会停止。shell 作业（例如为方便评审而启动的服务器）可以一直运行到派工结束。它们不占槽位，也不受 30 分钟上限约束，后续回合之后同样如此。它们的完成不会唤醒执行器；执行器在下一回合读取结果。

人也可以直接在执行器 Session 里发言来开启一个回合，其后台工作遵循同样的规则。

派工结束时，其 shell 作业会被终止且不唤醒 Session；子智能体被释放，它们所唤醒的完成回合一律丢弃。接替它的新派工及其等待中的输入，要等这次关停结束后才启动。

在 DeepSeek Harness 进程内停止或重启插件，走的也是同一套关停路径。尚未进入 Session 历史的输入会被保留。关停时为每个 worker 的后台工作最多等待 10 秒；若是进程重启，则直接结束这些工作。忙时被中断的派工，重启时会附带一条恢复说明。

worker 的子智能体（含嵌套子智能体）使用 DeepSeek Harness 的 `standard` 预设，并继承 worker 的权限。它们只保留 worker 被允许的工作工具，工单结束时这些工具一并失去。在 `standard` 下，shell 命令 60 秒后转入后台。子智能体结束时，其作业会被终止。

### 准备工作单目录

首次派工之前，若工单目录不存在，准备命令会在执行根目录下用 `sh` 执行一次，时限十分钟。若未配置准备命令，worker 会从一个空目录起步。

命令失败会使工单失败，并记录其输出。重试、或工单某个线程上出现人的消息，都会再尝试一次准备。典型命令用 `git worktree` 创建检出。当某个拉取请求的分支最后一段路径与工简短名一致时，它就归属于该工单。

### 并发

工单从启动那一刻起（含准备阶段）就占用一个 worker 槽位；若是从 `idle` 唤醒执行器，则从那次投递开始占用。整个活跃回合期间也持续占用该槽位。

配置的并发上限作用于这些槽位，另有一个额外槽位专门留给人的消息或状态请求。当常规槽位已满时，这类唤醒可以使用额外槽位，并且比新启动优先取得下一个空闲槽位。因此新工作不会挡住人继续处理已有工单。

其他输入（例如 CI 结果）等待常规槽位。启动会在 `working / queued` 中等到有槽位空出。各启动彼此并发，因此缓慢的准备命令只拖慢它自己那个工单。

### 执行变量

准备命令与执行器指令拿到的是同一组执行变量。命令读取环境变量；执行器在自己的提示词里读取这些变量的值与说明。其中不含任何凭据。

| 变量 | 注册方 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`, `DSH_SUPERAGENT_NAME`, `DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名与 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所监听的仓库，格式为 `owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`, `DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`, `DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 发起该工单的 Issue 或拉取请求；若是拉取请求，还包括其 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`, `DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及发起该工单的群聊 |

与工单相关的值来自其目录与最初的触发；其他值来自当前部署设置。只有面板能修改执行环境设置；发给主 Session 的文本改不了已配置的 shell 命令。

worker 通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被禁用的命令在按名称调用时会失败。

这些包装脚本与目录只是建立默认值，并不构成安全边界。worker 仍可通过绝对路径执行程序。

## 合并

自动合并由 **交付要求** 提示词管辖。宿主中没有专门针对合并的判定逻辑。

默认情况下，执行器绝不以智能体账号身份开启自动合并：GitHub 会把合并归到开启它的那个账号名下。「交付要求」必须写明用于合并的另一个账号的 CLI；没有写明时，由人来合并拉取请求。

默认指令只允许在下列条件同时满足时自动合并：拉取请求是为该工单开立的、已就绪、必需的批准覆盖 head 提交，且新增行数加删除行数合计少于 200 行。推送新一版修订之前，执行器会撤回自动合并。

没有正文的评审（例如批准）也会作为触发到达，并能唤醒正在等待评审的执行器。这些指令约束的是智能体，而不是 GitHub 的合并规则。若要强制要求批准，应在分支保护中设定，并让过期批准失效。省略合并用的 CLI、或删去自动合并段落，即可强制人工合并。

## 工单如何结束

- **就绪但没有拉取请求：** `ready` 报告会把工单以「已完成」结束。
- **无事可做：** 执行器若发现没有任何值得人去处理的工作，例如请求无法复现或已被取代，就报告 `dropped`。工单不发消息直接结束，除非命中的规则要求发一条；之后人在其线程上的消息可以恢复它。

### 拉取请求

执行器上报后，工单会关注它所源自的那个拉取请求；从它的分支开出的每个拉取请求，一经执行器上报、或被 GitHub 来源发现，也会纳入关注。重新开启的拉取请求会再次被关注。

当工单自己开出的拉取请求都不再处于开启状态时，工单即完成；若它没有开出任何拉取请求，则它所关注的全部拉取请求都必须关闭。随后它按最后一次相关关闭的结果结束，并保留订阅，使之后的人工评论能够恢复它。

若恢复、重试或故障恢复后的工作尚未完成，一次关闭不会结束工单。若执行器确认或答复了归它所有的追问，但此后既未提交非 `progress` 报告、也未在读完该消息后结束回合，工单同样会等待。之后一旦满足同一条拉取请求完成规则，后续的 `ready` 报告就会结束工单。

群聊渠道会收到一条关于拉取请求结果的最终通知；GitHub 上拉取请求本身就已展示该结果。移除工单对某个拉取请求的订阅，也会停止对该拉取请求的关注。

因此，「等待评审」指的是带拉取请求的 `ready` 报告。

### 追问与上下文线程

工单自身线程上的人工追问由执行器裁决。它处理范围内的请求，把超出范围或属于别的工单的请求交回。一旦没有任何执行器持有该消息，它就成为主 Session 的候选。除此之外，主 Session 对追问只能按人的请求停止工作。

一条输入在 Session 把它纳入某个步骤、并随后作出报告或结束回合之后，才算已读。工单结束时，既未确认、未答复、也未交回的未读消息会退回评估，详见 [002 授权](002-授权.md)；已读但未作处理的消息（例如一句道谢）则不会。

仅作上下文关注的线程仍会投递消息，但不会让工单取得人工追问的归属权，也不会恢复已结束的工单。这些消息可以被独立评估。

只要有活跃工单订阅，来源就会轮询已订阅线程；并从「最后一条触发」与「订阅工单结束」两者中较晚的那个时间点起，继续轮询两周。此后消息只通过常规入口到达：GitHub 通知或飞书实时事件。

## 故障与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、运行出错（记为 `failed`）时，工单不再接收自动输入。

模型提供方或网络的一过性故障——HTTP 408、429、5xx，或连接被拒、被重置、超时——会先按递增退避重试三次：重新启动一次；回合失败的 worker 会被告知继续；而失败的准备命令不重试。

一旦失败，CI 与机器人消息仍会记录在该工单上，但不会投递，也不会唤醒 Session。

它的工具仍然可用，因此人可以直接在 Session 里继续工作。

启动失败不会自行重试。

人的消息、之后一份既非 `blocked` 也非 `failed` 的报告，或一次重试，都会解除该冻结状态。

该状态由已存储的报告与输入推算得出，因此重启后依然保留。

### 重试

当开启中的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：对这三种情形，解决办法都是新开一个派工，重新启动 worker 并接走等待中的输入。

一旦人的消息送达受阻或失败的工单，执行器已拿到该消息，工单便显示为执行中（若失败的启动重新跑起来则显示为排队中），并且不再提供重试入口，除非那条消息本身投递失败。

重试会结束当前派工，并在同一个执行器 Session、目录、分支与拉取请求上开启一个新派工。

执行器模型设置只在创建 Session 时生效；已存在的 Session 保留原有模型。

### 重启

运行中的派工以「宿主已重启」结束，新派工则带着一条恢复说明启动：要求执行器在重复任何外部动作之前，先核对目录、git 历史与 GitHub；按工单从旧到新依次处理。

处于等待、就绪、受阻或失败状态的派工原样保留；除非在该报告之后又有输入送达，那种情况下它们也会重新启动。

Session、目录、订阅、待处理消息以及下文所述的已存储工作都能跨重启保留；每个执行器 Session 把哪些消息纳入了历史的记录也一样保留——步骤在认领消息之后、发起模型调用之前完成这一记录：被重启截断的那个回合所取走的消息，只要随后有报告或回合结束，就算已读；而某步骤已认领、但在写入历史前被取消或出错截断的消息，算作未读。

重试或重启时，会把「曾投递给它所替代的派工、但执行器 Session 并未取走」的消息重新交给新派工——取消或被截断的步骤可能丢过这些消息；若 Session 里还留着一份副本（由重启保留下来，或跨崩溃持久化下来的），会在新派工的第一条消息之前移除，确保新投递的那份是唯一副本。

### 已存储的工作

dsh-superagent 在一次决定之后要做的事——例如把候选、追问或报告转交给主 Session，启动派工，投递输入——都先落库，再执行。

转交或投递失败（例如 Session 不可达）时，2 秒后重试，随后按翻倍延迟重试、最长至一分钟；启动失败会使工单失败，除非是上文所说的一过性故障。

每一类工作只有在某一项连续失败三次后，才会在总览页的系统问题里报出错误；输入投递失败则显示在它所属的工单上。

向主 Session 的转交与通知都各自保持顺序；其中一条失败会挡住同类里排在它后面的消息。

### 来源故障

GitHub 来源分别读取每个 Issue、拉取请求与线程：某次读取失败会把错误留在其线程上，下次轮询再读一次，并计入来源的错误计数；默认连续三次轮询失败后，来源报出该错误；任何一次成功轮询都会把计数清零。

智能体失去对私有仓库的访问权限时，GitHub 同样返回 404，因此 404 也会重试。

已纳入通知的 Issue 或拉取请求若持续读取失败，会在首次失败一天后被丢弃；若 GitHub 明确报告它已删除，则立即丢弃。此后它不再使轮询失败，其线程保留错误，来源状态中也会记下它。

它的读取位置保持不动，因此之后的通知或对该线程的轮询，会把失败期间漏掉的内容补读回来。

飞书事件消费者会报告每一次失败；对已订阅话题的轮询则把每次失败留在其线程上。

GitHub 列表或飞书分页中格式不合法的条目会被跳过，并计入来源状态的计数。

### 渠道故障

外发消息会先存储，再作为已存储的工作发送；重试从 5 秒起按翻倍退避，最长到 300 秒。

同一工单发往同一会话的消息按入队顺序发出，因此确认消息排在后续的答复或结果之前：只要同一工单发往同一会话的更早一条还没发出，后一条就得等着，直到那一条连续失败三次并作为一个问题呈现出来。

其他工单的消息、以及不隶属任何工单的消息，不受它牵连。

有失败尝试的消息，在成功发出或被撤回之前，都会作为系统问题存在。

只有在来源不再监听该会话、或来源明确答复该会话永远无法接收时，消息才会被丢弃；来源关闭期间，消息继续等待。

在 GitHub 上，来源对已删除的 Issue 或已锁定的会话给出这种答复；在飞书上，则对被撤回的消息、或飞书已找不到的消息给出这种答复。

针对已不存在的评审评论的回复，会改发到该拉取请求的会话里。

被丢弃的消息仍保留记录，写明丢弃时间、原因以及所属工单，因此绝不会再次入队；被丢弃的确认消息在记录里是「已丢弃」，而不是「已发送」。

### 暂停处理

暂停会停掉派发、新的评估、评估超时、输入投递与回复；已经开始的启动会等到处理恢复。

来源继续记录触发，运行中的执行器回合不会被打断。

发给已结束工单的人的消息会等待：暂停结束后的第一轮处理会恢复该工单，前提是其授权在当时策略下仍然成立。

暂停期间，进行中的评估不会超时；其截止时间按暂停时长顺延。

### 配置不合法

若已存储的来源配置被其所属种类拒绝，该来源实例会被禁用。
