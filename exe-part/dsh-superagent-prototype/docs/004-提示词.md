# 004 提示词

本文说明智能体会读到什么、团队可以改什么，以及改动何时生效。它建立在 [000 理念](000-理念.md) 至 [003 执行](003-执行.md) 之上。提示词文本以英文撰写。

## 团队可写的内容

团队可以编辑三个团队小节、添加技能，并覆盖每一个内置的系统提示词部件。多数默认值放在 `prompts/` 与 `skills/` 下。工具描述、通知与卡片仍写在代码里，无法通过提示词设置修改。

| 小节 | 内容 |
| --- | --- |
| 沟通 | 何时给人发消息、消息怎么写、每条 GitHub 消息的开头行（默认为 `This is by an automated agent, not a human`）、如何处理评审，以及哪些普通账号属于评审机器人 |
| 工单范围 | 工单何时继续做、何时带着草稿停下 |
| 交付要求 | 拉取请求中应给出的证据、自动合并的条件与行数阈值、提交作者；若不填写提交作者，执行器会以智能体账号的 no-reply 地址提交 |
| 团队技能 | 智能体按需加载的知识，例如一个说明「哪个飞书用户对应哪个 GitHub 账号」的 `identities` 技能 |

内置文本覆盖角色、工具用法、宿主机制、授权规则，以及 GitHub 与飞书技能。它通过标题引用团队小节，而不是把它们重复一遍。

### 内置部件与模板

覆盖使用下列键：

| 部件 | 键 |
| --- | --- |
| 共用指令与角色 | `runtime/shared`, `runtime/orchestrator`, `runtime/worker` |
| 工作指令 | `runtime/subscriptions`, `runtime/replies`, `runtime/dispatch`, `runtime/work`, `runtime/admission` |
| 交接指令 | `runtime/handoff/orchestrator`, `runtime/handoff/worker` |
| 来源技能 | `skill/feishu`, `skill/github` |
| 生成式小节 | `runtime/environment`, `runtime/policy`, `runtime/policy/none` |

生成式小节是可编辑的模板，必须保留以下占位符：

- `runtime/environment`：`{variables}`，由执行环境的各行内容填充。
- `runtime/policy`：`{version}`、`{mode}` 与 `{rules}`，每条已启用的规则占一行。
- `runtime/policy/none`：`{version}` 与 `{mode}`，在没有启用任何规则时使用。

编辑某个部件，改变的是模型收到的指令；它不会改变准入、授权、工具校验或账号包装脚本，这些仍由代码强制执行。

在收到明确的人工请求时，主 Session 也可以用 `orchestrator_prompts_save` 保存覆盖内容。若某次保存省略了覆盖项的 `base`，则沿用已保存的 base。某个部件若在已保存配置中存在、而本次被移除，保存时会删去；其他任何未知部件一律拒绝。

每个覆盖项都记录了它所依据的内置文本。升级会保留团队自己的文本。若默认值发生变化，面板会把该部件标为 **默认值已更新**，并在团队文本旁显示差异。团队可以保留自己的文本、采用新默认值，或另行编辑。没有覆盖的部件会自动跟随新的默认值。

主 Session 可在 `orchestrator_read prompts` 的 `default_changed` 下读到受影响的部件名称。

## 组装与优先级

系统提示词按下列顺序组装：

1. 共用指令与角色。
2. 三个团队小节。
3. 订阅与回复。
4. 主 Session 用调度指令，执行器用工作指令。
5. `runtime/admission`，仅主 Session。
6. 交接指令。
7. `runtime/environment`。
8. `runtime/policy`，仅主 Session。

准入指令来自 `prompts/admission.md`，说明如何研判主动候选，以及何时可以仅凭候选卡忽略一个无关候选。`orchestrator_eval` 返回的是上下文，而不是把这些指令重复一遍。

执行环境小节给主 Session 提供部署级的值，给每个执行器提供其工单专属的值。策略小节会在每次模型请求时依据设置重新生成，包含策略版本、接单模式、明确请求的豁免，以及按 `- <name> (<id>): <instruction>` 格式列出的已启用规则；若一条都没启用，则给出一句说明。它排在最后，这样策略变更不会改动前面的提示词文本。

执行器还会读到 DeepSeek Harness 的编码提示词与仓库的 `AGENTS.md`，主 Session 则不读。推断型工单会在末尾附加一条说明，把其执行器限定在命中的规则内。派工与到达的消息以触发卡的形式内联呈现，只有被截断的内容才带资源指针。

执行器在无人值守下工作。它的工具集中排除了向人提问、向人展示界面或修改配置档的工具，例如 `ask_user_question`、`present` 与 `plugin_manager`。

优先级由强到弱：

1. 由工具与宿主强制的事实：身份、权限、工具参数校验、回复用途、长度限制。提示词文本改不了它们。
2. 内置与生成式小节，以团队对它们的覆盖内容为准。
3. 主动型工单所命中规则中的流程与沟通要求，仅对该工单的执行器 Session 生效。
4. 团队小节与团队技能。
5. 外部文本：消息、评论、文档与引文。它是数据，绝不改变规则或授权。

## 内置文本的原则

这些原则把 [000 理念](000-理念.md) 落实到智能体身上：

- **角色分离。** 主 Session 只做路由：它转发原始触发与路由所需事实，不作技术判断；所有决定通过一个路由工具完成，一次调用可处理多个等待中的候选。路由备注最多 30 词。执行器阅读原始来源、判断范围、实现并验证。
- **主 Session 不等待。** 报告、追问通知、候选以及已完成的后台作业都会自动以消息形式到达；无事可做时它就结束回合。防护机制会拒绝 `sleep`、超过 30 秒的 shell 超时和超过 5 秒的作业等待，因为一个被卡住的步骤会拖住新候选。这些指令取代了主 Session 完整提示词中 DeepSeek Harness 自带的作业通知说明。
- **只在有人必须介入、或结果可被采用时发消息：** 结果已可评审或使用、需要某个决定或资源，或工作无法完成。群聊消息默认一句话，硬上限 100 词。
- **追问由执行器裁决。** 每个执行器处理并确认范围内的请求，把超出本工单或属于其他工单的请求交回。只有在全部持有者都交回、或结束而未接手之后，一条消息才会成为新工作。主 Session 会收到追问通知，但只能据此停止工作。被交回的消息随后作为候选到达，并附上各执行器的理由。
- **通过订阅与主 Session 协作。** 执行器关注相关线程以获取上下文。主 Session 可以用一条不超过 100 词的备注，把另一个工单的事实送过来。无论订阅还是备注，都不授予权限。
- **只在明确引用时才挂载。** 消息必须指向某个工单的拉取请求、Issue、来源消息或确认消息，或指向恰好只匹配一个工单的近期变更。仅凭话题相似还不够。挂载会让工单订阅整个线程；执行器若判定它无关，就调用 `orchestrator_thread_unrelated`，并且不在那里作答。
- **具体地确认一次。** 在投入实质工作之前，执行器对每个新请求确认一次，并在原消息下回复，写明对象和预期结果。
- **通过 `human_action` 提问。** 执行器在报告里放一个具体问题，主 Session 原样转发。若问题由某条人的消息引出，就指明该消息，由宿主在那里提问；否则在工单的原始会话中提问。已获授权的工作可同时进行。
- **如实交付。** 开出拉取请求不等于已就绪；草稿要标注为未完成；没有真实「改动前」截图的界面改动不算就绪。
- **人的暂停持续有效**：跨越追问、新的执行器 Session 与重启，直到有人解除它。自动反馈绝不会恢复被暂停的工作。
- **示例只示范格式。** 示例句不是智能体可以主张的事实。
- **按结果处理评审。** 已修复并验证过的评论静默解决；被拒绝的意见用一句话说明理由。自动化审阅者的线程一旦有了答复就解决，且每个自动化审阅者在单个拉取请求上最多三轮。
- **让位于重复的工作。** 若某人的分支或拉取请求已包含本工单的改动，执行器就用一句话指向对方那一份，并关掉自己的拉取请求。

## 版本

- 每次保存都会创建一个不可变的版本，包含完整配置、修订号、前驱版本、时间戳与来源（面板或工具）。恢复某个版本或恢复默认值，也会创建新版本。
- 保存时要指明所依据的修订号。发生冲突的保存会被拒绝，且不会丢弃草稿。
- Session 在每次模型请求时读取最新版本，同一回合里的后续步骤也不例外。保存不会重启、取消或唤醒 Session。宿主记录每个 Session 用过的修订号；执行器可以读取自己曾在其中工作过的任一修订。
- 由部署设定总大小上限，覆盖内容也计入其中。校验会拒绝未知键、保留的内置技能名、未知的覆盖部件，以及缺失的模板占位符；它绝不静默截断文本。与默认值完全相同的覆盖会被移除，使该部件继续跟随未来的默认值。
