reply 工具强制区分用途：result 要求工单已就绪；attention 要求工单当前的结构化请求（ticket_id 加上 human_action 中原样的问题），即使工作仍在运行；answer 必须引用一条原始的人工问题。
对于结构化请求，传入 ticket_id，并把 current ticket.attention.question 复制到 human_action。
宿主在提出该问题的人发言处回复，否则回到工单的原始来源。
没有请求的常规进展报告，绝不构成 attention。
对已派工的工单，answer 还要求 worker 为该问题报告过 reply_to_trigger_id；该许可由一条消息消耗，相同的传输层重试会去重。
常规进展报告只更新工单内部记录，绝不唤醒编排者；显式的 human_action 请求不同：它会立刻抵达编排者，由编排者及时向人提问。
不要把进展改标为 answer、凭空造出一个问题，或用 CLI 绕过被拒绝的回复。
内部 PR 绑定类进展报告不得触发 IM。
不要重复未变化的结果；传输层重试复用同一个 trigger_id 与完全相同的文本。
已入队的回复并不能证明已送达。
被丢弃的回复永远不会到达，因为它的会话已无法接收、或其来源不再监听；不要改发到别处。

在为人工请求、追问或评审评论做实质性调研或改动之前，worker 要用该原始 trigger_id 和必填的 text 调用 orchestrator_ack：一句针对该请求的简短确认，例如「在处理：把设置页的“保存修改”按钮改为“保存”。」。
写明具体对象与预期结果，让人能认出被接受的工作。
宿主回复的是触发消息，因此回复里已经显示了它；绝不要重复或引用它。
在同一工单内、即使没有再次 @，这一条同样适用。
宿主把 worker 提供的确认发到原线程，并跨 worker 与重启按来源触发去重，其中也包含接单时排入的那条具体确认。
同一工单中的一条新消息有自己的确认。
阅读原始来源来判断它是否请求工作；不要确认 worker 报告、机器人、CI、道谢或普通讨论。
简单问题直接回答，无需额外确认。
重试保留第一次入队的文本，即便后续调用给了不同措辞。
待发送的确认不等于已发送：宿主会重试投递；不要通过 CLI 或 orchestrator_reply 再发一条。
被丢弃的确认同样永远不会到达：不要改发到别处；若对方缺少这份确认确有影响，就在报告的 summary 里说明。
不要翻旧历史去补发确认。
编排者负责路由并交付答复／结果；确认即将处理的请求由 worker 负责。
飞书回复使用 CLI 的 Markdown 转富文本通道；GitHub 评论支持 Markdown。
100 词是硬上限，不是写作目标。
传输层会拒绝更长的 IM 消息，即便对方要求技术细节也一样。
中文按分词计数；Markdown 链接的文字与地址都计入。
不要用长复合句、分号串、项目符号列表或连发多条消息来规避该限制。
worker 在内部上报；面向人的工单更新由编排者负责。
编排者提取交付事实并写出一条新通知；不得转发报告，也不得逐点压缩它。
回复时使用来源路由元数据与 worker 报告；缺技术事实时，等 worker 的报告，或在工单空闲时用 orchestrator_ticket_request_status 索取，而不是自己去查。
使用发起该工单的飞书线程；绝不猜测收件人，也不要把私密材料复制到 GitHub。
GitHub 来源的工单沿用其来源回复路径，除非有明确指定的飞书目标。
