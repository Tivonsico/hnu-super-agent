# 安装配置

本文是给智能体的操作指引，用于陪同操作者完成 dsh-superagent 的安装配置。如果你是用户本人，请让你的编码智能体阅读本文件并照此执行。

## 安装流程如何执行

安装流程遵循 [docs/000-理念.md](docs/000-理念.md)：尽可能少地占用操作者的注意力。

- **在提出第一个问题之前**，只阅读本文件与 `docs/000-理念.md`，并运行一次下文的探测命令。在收齐全部答复之前，不要阅读其他文件。
- **每条消息只问一个问题**，且只涉及一件事。得到答复后再问下一个。探测命令已经能回答的问题直接跳过。
- **每条消息控制在 300 词以内**，除非操作者要求更详细。为每个问题给出一个推荐答案，让操作者用一个词即可采纳，并用一句话说明它为何重要。
- **提问期间不要执行任何操作。** 收齐全部答复后，用一条消息给出完整方案，待操作者确认后才开始执行。
- **绝不在对话中索要密钥。** 需要操作者亲自动手的步骤，例如创建账号、登录命令行工具或填入应用密钥，集中放进一条消息，并附上要他们在自己终端中执行的确切命令。
- **把设计理念融入提问**，每次一句话，不要变成说教。

## 1. 环境探测

在本仓库的检出目录中运行一次，结果自行保留、无需展示给操作者：

```sh
node -v; pnpm -v; git --version; tmux -V; python3 --version; gh --version | head -1; dsh --version
gh api user --jq .login
command -v lark-cli
grep -l -E 'id: dsh-superagent\b' "${DSH_HOME:-$HOME/.dsh}"/profiles/*/cordis.patch.yml 2>/dev/null
```

- **前置条件：** Node.js 22.19+ 或 24+、pnpm、git 2.32+、tmux、Python 3.8+、GitHub CLI 2.48+，以及版本落在 `package.json` 中 `engines.dsh` 区间内的 DSH。缺少任何一项都作为方案里的待办事项列出，而不是向操作者提问。DSH 还需要一个模型提供方；若操作者从未带模型运行过 DSH，配置模型属于操作者步骤。
- **操作者登录名：** `gh api user` 的结果是操作者本人的 GitHub 登录名，用作第 5 问的推荐答案。
- **已有配置档（profile）：** 若某个配置档的 `cordis.patch.yml` 中含有 `dsh-superagent` 条目，说明此前已经安装过：询问是否在此基础上继续、是否保留原有配置，并阅读 `docs/006-部署运维.md` 的「升级」一节。

## 2. 提问

按下列顺序、每条消息一问，遵循 [docs/001-领域模型.md](docs/001-领域模型.md) 中的工作流向：先问触发（Trigger）从何而来，再问谁可以在那些渠道提出工作请求，最后问执行器（Executor）如何处理工单（Ticket）。方括号内为推荐答案。

**来源：请求从何而来。**

1. **来源渠道。** 智能体只接收来自 GitHub 的请求，还是也接收飞书群聊中的请求？［推荐：仅 GitHub，除非团队日常在飞书协作。］
2. **目标仓库。** 智能体应在 github.com 上的哪个仓库工作？请按 `owner/name` 格式给出。
3. **智能体账号。** 智能体以哪个 GitHub 用户账号的身份行动？［推荐：一个专用账号，绝不使用操作者本人账号：智能体写下的所有内容都会显示在这个名字之下。］该账号可能尚未创建，创建它属于操作者步骤。
4. 若接入飞书：**接入哪些群聊**？请给出群名称。机器人配置完成后，智能体会自行查出对应的 id。

**策略：谁可以提出工作请求。**

5. **在 GitHub 上。** 哪些 GitHub 登录名可以向智能体分派工作？［推荐：仅 `<操作者登录名>`：智能体只为名单上的人行动；在操作者熟悉其行为之前，名单短一些能减少对团队的干扰。］
6. 若接入飞书：**谁可以在飞书里提出请求？**［推荐：第一个群聊中的全体成员，并随群成员变动保持同步。］

**执行：智能体如何处理工单。**

7. **代码检出。** 每个工单应从仓库的哪一份本地克隆检出代码？［推荐：在 `~/src/<name>` 下新建一份克隆。］
8. **提交身份。** 智能体产生的提交应署名谁为作者？［推荐：智能体账号，这样它的工作一眼可辨。］若要使用其他身份（例如操作者本人），需写进提示词的「交付要求」小节。
9. **自动合并。** 当智能体自己创建的拉取请求准备就绪且获得批准后，是否由它开启自动合并？［推荐：否；先由人工合并，直到智能体提交的拉取请求连续一段时间都正确无误。］智能体绝不会以自身账号身份开启自动合并，因此若选「是」，还需要另一个具备合并权限账号的 GitHub CLI：请在操作者步骤中让操作者登录该账号，并在「交付要求」中写明它。若选「否」，则从「交付要求」中删去自动合并相关段落。

已有合理默认值的配置项不要拿来提问，直接列入方案：

- 配置档名为 `superagent`，是 DSH Web 配置档的一份副本，与操作者日常使用的配置档彼此隔离，因此重启它不会关闭操作者的 Session；端口 `3082`；状态目录使用绝对路径 `<home>/.dsh/state/superagent`；
- 从操作者自己的配置档发起每小时一次的巡检，在 dsh-superagent 未运行时将其修复；
- 分支前缀 `agent/`；
- 接单模式为 `observe`，即只记录主动发现的工作而不实际执行，并采用默认规则与默认提示词小节；
- 若接入飞书：机器人只读取 @ 提及它的消息，并开启私聊消息。

## 3. 方案

用一条不超过 300 词的消息说明：将安装什么、需要哪些账号与命令行工具、要保存哪些配置、操作者需完成哪些步骤，以及采用的默认值。只请求一次确认。

## 4. 执行

1. **先完成操作者步骤。** 阅读 `docs/006-部署运维.md` 的「账号」一节，自行写好各命令行工具的包装脚本（wrapper），然后用一条消息列出只有操作者能做的事：创建智能体账号；若启用自动合并，以负责开启自动合并的账号登录一份 CLI；以智能体账号接受仓库邀请；为每个包装脚本执行 `auth login`；若接入飞书，创建并发布机器人应用，并用其密钥执行 `config init` 命令。等操作者回复完成后，用 `<wrapper> api user --jq .login` 逐一核验登录身份。
2. **安装并启动。** 按 `docs/006-部署运维.md` 的「安装」「机器配置」「启动与停止」三节执行。跳过克隆本仓库的 `git clone`：你已经在它的检出目录中。若第 7 问要求新建克隆，则克隆第 2 问指定的仓库。若已有配置档，跳过 `dsh superagent --from-default-profile` 命令——它会替换配置档并删掉其中的 `cordis.patch.yml`；此时应直接编辑该文件，而不是替换它。
3. **配置。** 按 `docs/006-部署运维.md` 的「管理 API」一节，依下列顺序保存设置：`github` 来源；若使用飞书则还有 `feishu` 来源；带许可名单的 `policy` 配置块（若接入飞书，先用机器人的 CLI 查出群聊 id）；以及带第 7 问所得准备命令的 `executor` 配置块。随后保存提示词，把第 8 问的提交身份与第 9 问的自动合并答复写入「交付要求」。若某次保存返回 `restarting: true`，表示 dsh-superagent 正在重启：在发起下一次请求之前，先等到 `scripts/dsh-superagent status` 不再以退出码 1 结束，并通过 `GET settings` 重新读取各配置的修订号。
4. **失败处理。** 保存被拒绝时，响应体会写明具体的安装问题。在 `docs/006-部署运维.md` 的「故障排查」表中找到对应条目、修复后继续。只有自己无法解决的问题才去询问操作者。

## 5. 验证与交接

`scripts/dsh-superagent status` 以退出码 0 结束且未报告安装问题。若你运行在操作者自己的 DSH 配置档中，用你的定时任务工具按 `docs/006-部署运维.md` 的「每小时巡检」一节创建该巡检；否则把用于创建巡检的提示词交给操作者，让他在该配置档里排定。随后发送一条不超过 300 词的消息，说明：

- 控制面板地址，并说明侧边栏中的 **Superagent** 入口就是查看位置。
- 试用方法：用许可名单上的账号，在仓库的某个 issue 下评论 `@<智能体登录名> <请求内容>`。约一分钟后，总览页会出现一个工单。
- 从 `docs/000-理念.md` 的「责任」一节提炼出给操作者的三条准则：起步时收窄范围、持续调优以减少干扰、对智能体说出口的话负责。
- 延伸阅读：`docs/` 下的编号文档，按顺序阅读。
