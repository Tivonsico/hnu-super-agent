# 消息层 × 前端

会前草案。前端负责采集用户输入、保存本次操作 ID、显示返回状态。消息层接全局输入和指定合并，读取消息状态；已有工单的其他操作由工单程序或执行层处理。

| 界面动作 | 接收者 | 结果 |
|---|---|---|
| 全局输入 | 消息层 | 保留原文和附件引用，入队后返回包 ID。 |
| 指定 A 合并到 B | 消息层 → Router → B 的 Worker | 包中记录两个工单 ID。Router 下达指令，B 的 Worker 处理工单。 |
| 恢复 C 可见性 | 确定性工单程序 | 更新 C 的可见性，Router 后续查询可以读到 C。 |
| 补充、反馈、终止 | 执行层的工单 steer | 通过既有工单操作入口处理。 |
| 确认成果、刷新工单 | 工单程序 | 确认追加节点；刷新读取工单记录。 |
| 监听设置、消息积压和通知 | 消息层及通知存储 | 页面读到已保存配置、实际生效版本、待交接数量和未读提示。 |

### 提交消息包与刷新

原型使用本地 HTTP。正式前端可以沿用下面的请求形状。所有写请求以 JSON 提交，错误体至少含 `code`。一次意图生成一个 `operation_id`。超时后同一意图沿用原 ID，用户改了内容后生成新 ID。

| 方法 | 请求 | 返回 |
|---|---|---|
| `POST /api/packages` | `{"kind":"new_task","operation_id":"op-018","text":"整理实验报告","attachment_refs":[{"id":"template-017"}]}` | HTTP 202，`{"code":"QUEUED","package_ref":{"id":"pkg-018"}}` |
| `POST /api/packages` | `{"kind":"merge","operation_id":"op-019","source_ticket_id":"A","target_ticket_id":"B"}` | HTTP 202，`{"code":"QUEUED","package_ref":{"id":"pkg-019"}}` |
| `GET /api/packages/pkg-019` | 无请求体 | HTTP 200，`{"code":"OK","package":{"package_ref":{"id":"pkg-019"},"kind":"merge","operation_id":"op-019","source_ticket_id":"A","target_ticket_id":"B","state":"ACCEPTED","code":"OK","receipt_id":"ack-019"}}` |
| `GET /api/state` | 无请求体 | `{"code":"OK","packages":[],"router_acceptance":[],"tickets":[{"id":"A","visible":1}]}`，列表按实际数据返回。 |
| `POST /api/tickets/restore` | `{"ticket_id":"C"}` | HTTP 200，`{"code":"OK","ticket_id":"C","visible":1}`，重复恢复返回 `REPLAYED`。 |

文本不能为空，附件引用可省，合并的两个工单 ID 必填且不同。正式界面从工单选择器获得 ID，无需从用户输入的自然语言解析合并方向。提交成功时显示消息包交接状态。工单程序后续提供的结果单独显示，包状态为 `ACCEPTED` 表示执行侧接管完成。

| 消息包状态 | 页面显示 | 此时前端如何处理 |
|---|---|---|
| `QUEUED` | 排队中 | 保存包引用，用于后续查状态。 |
| `AWAITING_ACK` | 等待接管 | 保持当前包，可刷新。 |
| `RETRY_WAIT` | 待重试 | 显示最近一次原因，原包仍在，由看门狗重试。 |
| `ACCEPTED` | 已接管 | 保留包和回执供查看。 |

收到 `REPLAYED` 使用返回的原包。遇到 `INVALID_INPUT` 保留原文并指出无效字段；遇到 `CONFLICT` 重新读取原操作结果或当前配置。消息层未收到 Router 回执使用 `ACK_UNKNOWN`，此时页面应展示交接不确定，沿原引用查询即可。

### 监听设置与状态提示

| 方法 | 请求 | 示例返回 |
|---|---|---|
| `GET /api/settings` | 无请求体 | `{"code":"OK","enabled":true,"saved_revision":3,"effective_revision":3}` |
| `POST /api/settings` | `{"enabled":false,"expected_revision":3}` | `{"code":"OK","enabled":false,"saved_revision":4,"effective_revision":4}` |
| `GET /api/health` | 无请求体 | `{"code":"OK","source":"SIMULATED","pending":2,"gaps":[]}` |
| `GET /api/notifications?unread=true` | 可选只读过滤条件 | `{"code":"OK","items":[{"id":"notice-017","origin":"execution","code":"MODEL_QUOTA_EXHAUSTED","read":false}]}` |
| `POST /api/notifications/notice-017/read` | `{}` | `{"code":"OK","id":"notice-017","read":true}` |

1. 原型只演示全局监听开关。正式界面建议按 QQ 账号和会话选择作用范围，另传作用范围、发起人 ID 列表和操作 ID。开关为布尔值，版本为非负整数。保存版本大于生效版本时，页面显示尚未生效。
2. 正式健康接口可返回来源状态 `CONNECTED`、`DISCONNECTED` 或 `BACKFILLING`，以及缺口起止时间和原因。来源连接、待交接数量及执行侧错误各自显示。
3. 通知读取和标记已读是假设接口。执行侧不足额或异常时由发现问题的程序写通知。前端根据错误码渲染具体状态，重开页面可读取尚未处理的记录。

### 浏览器演示

- 添加一条示例 QQ 消息，点击「运行一轮看门狗」。在同一列表项上看到「排队中」变成「已接管」，展开「接口数据」查看原包及回执。
- 另加一包，切换「接管后丢失回执」，运行后显示「待重试」。切回「正常接管」再次运行，查看返回的原接管回执。
- 选择「指定合并」并提交 A 到 B，查看包里的两张工单 ID。这个原型演示到执行侧接管为止。
- 对 C 点击「恢复可见」，确认 C 变为「可见」，包列表保持原有内容。

页面当前提供组包、看门狗演示和恢复。监听与健康已有可调用的假接口，持久通知和完整工单页面按上述契约接入。联调脚本 `python3 verify.py` 可验证这些已实现的请求及重启后的行为。
