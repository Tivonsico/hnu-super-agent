调用签名使用 TypeScript 记法。HNU 工具传入 JSON 对象，签名中的类型名与本条字段表或 06 的数据定义对应。示例中的 `arguments`、`result` 分别是输入和输出。[06 执行层流程图](06_执行层流程图.svg)

### `readPackage`

| 项目 | 约定 |
|---|---|
| 调用签名 | `readPackage(args: { package_id: string }): Promise<RawBatch \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | Router、Worker → 消息存储，执行宿主注册工具。 |
| 调用时机 | Router 判断新包。Worker 处理新要求或回查工单关联的包。 |
| 参数 | `{package_id:string}`。取 Router 输入的 `package_id`、Worker 的 `input.package_ref.id` 或工单中的包引用。 |
| 调用条件 | ID 至少含一个非空白字符，指向已封存的消息包。 |
| 回执 | `{code:"OK",records:RawRecord[],missing_refs:Ref[]}`。直接返回包内原始文字和文件记录。 |
| 错误 | `INVALID_INPUT` 为参数不符，`REF_NOT_FOUND` 为包不存在，`STORE_UNAVAILABLE` 为存储读取失败。 |

**执行步骤**

1. 从包索引查原件 ID。封包前原件已按条入库，已封存的包和被引用的原件按原 ID 保留。
2. 用 `readRawInBatch` 的批读逻辑读取成员。先去重，再按发送时刻升序返回。同一时刻沿用包内首次引用顺序，确实缺失的成员进入 `missing_refs`。

**工具定义**

```json
{
  "name": "readPackage",
  "description": "按包 ID 一次读取该包选中的全部原始文字和文件记录。",
  "parameters": {
    "type": "object",
    "properties": {"package_id": {"type": "string", "minLength": 1, "pattern": "\\S"}},
    "required": ["package_id"],
    "additionalProperties": false
  }
}
```

### `readRawInBatch`

| 项目 | 约定 |
|---|---|
| 调用签名 | `readRawInBatch(args: { raw_ids: string[] }): Promise<RawBatch \| StoreError<"INVALID_INPUT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | Router、Worker → 消息存储。 |
| 调用时机 | 持有原始消息或文件 ID，需要按原引用回读。单条也用本工具。 |
| 参数 | `{raw_ids:string[]}`。数组可以为空，元素取原始记录的 `ref.id`，每个 ID 至少含一个非空白字符。 |
| 调用条件 | 回复前文的关联用同来源、账号和会话内的 `message_id` 找原记录，回读仍传 `ref.id`。 |
| 回执 | `{code:"OK",records:RawRecord[],missing_refs:Ref[]}`。空输入返回两个空数组。 |
| 错误 | `INVALID_INPUT` 为参数不符，`STORE_UNAVAILABLE` 为存储读取失败。 |

**执行步骤**

1. 按 ID 首次出现顺序去重，一次查原始记录索引。文字和文件使用同一记录结构。
2. 把找到的记录按 `sent_at` 的实际时刻升序排列，同一时刻保持输入顺序。确实不存在的 ID 按输入顺序列入 `missing_refs`。
3. 调用方可继续使用已返回的原件。必需材料缺失时按原 ID 查找或请用户补充。

**工具定义**

```json
{
  "name": "readRawInBatch",
  "description": "按原始记录 ID 批读文字和文件，按发送时刻返回。",
  "parameters": {
    "type": "object",
    "properties": {"raw_ids": {"type": "array", "items": {"type": "string", "minLength": 1, "pattern": "\\S"}}},
    "required": ["raw_ids"],
    "additionalProperties": false
  }
}
```

**示例**

```json
{
  "arguments": {"raw_ids": ["raw-404", "raw-017", "raw-017"]},
  "result": {
    "code": "OK",
    "records": [
      {
        "ref": {"id": "raw-017"},
        "type": "text",
        "source": "qq",
        "account_id": "qq-1",
        "conversation_id": "volunteer-1",
        "message_id": "msg-095",
        "sender_id": "teacher-liu",
        "sent_at": "2026-11-17T20:30:00+08:00",
        "reply_to_message_id": null,
        "content": "请按学校模板做志愿活动 PPT。"
      }
    ],
    "missing_refs": [{"id": "raw-404"}]
  }
}
```

### `readCandidateTickets`

| 项目 | 约定 |
|---|---|
| 调用签名 | `readCandidateTickets(args: Record<string, never>): Promise<CandidateList \| StoreError<"INVALID_INPUT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | Router → 工单存储。 |
| 调用时机 | 每个包读完原文后调用，再决定新建、归入或忽略。 |
| 参数 | `{}`。 |
| 调用条件 | 候选依据为已提交的工单。Router 负责判断主题。 |
| 回执 | 返回数组，每项为 `{ticket_id:string,title:string,description:{text:string,visible:1}}`。无候选时为 `[]`。 |
| 错误 | `INVALID_INPUT` 为请求带了参数，`STORE_UNAVAILABLE` 为工单视图读取失败。 |

**执行步骤**

1. 宿主从工单固定头和节点序列生成简述，启动时可重建。发布节点后更新内存中的对应条目。
2. 只查询 `description.visible == 1` 的工单。初始值为 1，`stop` 或 `merge_out` 使其变为 0，`resume` 使其变为 1，其他节点沿用原值。
3. Router 用 `read` 打开主题相近工单的 JSONL，再决定去向。归入投递前由宿主复核目标可见性。

**工具定义**

```json
{
  "name": "readCandidateTickets",
  "description": "返回所有可见的工单简述，供 Router 匹配。",
  "parameters": {"type": "object", "properties": {}, "required": [], "additionalProperties": false}
}
```

**示例**

```json
{
  "arguments": {},
  "result": [
    {"ticket_id": "B", "title": "志愿活动 PPT", "description": {"text": "按学校模板制作活动说明。", "visible": 1}},
    {"ticket_id": "D", "title": "英语演讲报名", "description": {"text": "填好英语演讲比赛报名表。", "visible": 1}}
  ]
}
```

### `askDownloadFile`

| 项目 | 约定 |
|---|---|
| 调用签名 | `askDownloadFile(args: { raw_id: string }): Promise<string \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE" \| "AUTHORIZATION_REQUIRED">>` |
| 调用方 → 责任方 | Worker 或其宿主 → 消息存储及来源下载程序。 |
| 调用时机 | 已知原始文件 ID，需要取得已有副本路径或下载。 |
| 参数 | `{raw_id:string}`。取 `type:"file"` 的原始记录 `ref.id`，ID 至少含一个非空白字符。 |
| 调用条件 | 文件待下载或已下载副本缺失时，宿主按当前工单及该 `raw_id` 校验用户的 `allow` 回执。 |
| 回执 | 成功返回文件副本的实际绝对路径字符串，Worker 可直接打开。 |
| 错误 | `INVALID_INPUT` 为参数不符或记录为文字，`REF_NOT_FOUND` 为原件不存在，`AUTHORIZATION_REQUIRED` 为缺少许可，`CONFLICT` 为无法取回，`STORE_UNAVAILABLE` 为临时读写或来源故障。 |

**执行步骤**

1. 按 `raw_id` 查文件记录。状态为 `DOWNLOADED` 且副本可读时，直接返回已存路径。状态为 `UNAVAILABLE` 时返回 `CONFLICT`。
2. 需要下载时先校验授权，再由消息层按来源索引下载。同一原件的并发请求复用一次下载。
3. 完整副本落盘并可读后保存路径和 `DOWNLOADED`。已过期等无法取回时记为 `UNAVAILABLE`。

**工具定义**

```json
{
  "name": "askDownloadFile",
  "description": "按文件记录 ID 获取已授权文件的本地绝对路径。",
  "parameters": {
    "type": "object",
    "properties": {"raw_id": {"type": "string", "minLength": 1, "pattern": "\\S"}},
    "required": ["raw_id"],
    "additionalProperties": false
  }
}
```

**示例**

```json
{"arguments": {"raw_id": "raw-018"}, "result": "/hnu/superdot/downloads/raw-018/志愿活动模板.pptx"}
```

## 工单写入工具

注册用的参数和返回类型取 06 的 `contract.interfaces` 与 `contract.schema.$defs`。工单 ID 和节点 ID 的各段以 ASCII 字母或数字开头，后续可用 ASCII 字母、数字、下划线和连字符。[06 执行层流程图](06_执行层流程图.svg)

### `createTicket`

| 项目 | 约定 |
|---|---|
| 调用签名 | `createTicket(args: CreateTicketArgs): Promise<TicketWriteReceipt \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | Router → 执行宿主／工单存储。 |
| 调用时机 | 已查过全部可见候选并读完匹配详情，确认本包需要新建工单。 |
| 参数 | `{package_id,ticket_id,title,description,requirement}`，均为非空字符串。`package_id` 取当前包，`ticket_id` 取 Router 输入的 `new_ticket_id`。 |
| 调用条件 | 本包已接管。本轮已完成 `readCandidateTickets({})`，空候选返回 `[]` 时也算完成检索。 |
| 回执 | `{code:"OK" \| "REPLAYED",ticket_id:string}`，`ticket_id` 为本次工单号。 |
| 错误 | `INVALID_INPUT` 参数或绑定不符，`REF_NOT_FOUND` 找不到原包，`CONFLICT` 同包建单参数冲突，`STORE_UNAVAILABLE` 写入失败。 |

**执行步骤**

1. 按包 ID 核对已有建单记录。宿主保存工单头，`description` 写入 `description.text`。首个 `requirement` 的正文取 `requirement`，引用原包和 Router Session。
2. 工单头、首节点和待派工输入都保存后回执。宿主用工单 ID、原包引用和首节点 ID 启动 Worker。原样重试沿用工单号与节点。

**示例**

```json
[
  {"arguments": {"package_id": "pkg-017", "ticket_id": "B", "title": "志愿活动 PPT", "description": "按学校模板制作活动说明。", "requirement": "请按学校模板做志愿活动 PPT。"}, "result": {"code": "OK", "ticket_id": "B"}}
]
```

### `appendTicketNote`

| 项目 | 约定 |
|---|---|
| 调用签名 | `appendTicketNote(args: AppendTicketNoteArgs): Promise<CommitAck \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | 当前工单 Worker → 执行宿主／工单存储。 |
| 调用时机 | 给本单登记归入的新包、成果、卡点、解除记录或本轮 Note。 |
| 参数 | `{ticket_id:string,node:{node_id,kind,text,refs}}`。`node` 使用工单节点字段。`text` 非空，`refs:EvidenceRef[]`。 |
| 调用条件 | `ticket_id` 是本单。节点 ID 以本单 ID 加 `/` 开头，通常由 Worker 预先分配。归入包时使用交付的 `input_node_id` 与 `package_ref.id`。引用须能回查。 |
| 回执 | `{code:"OK" \| "REPLAYED"}`。文件和该节点都提交后确认。 |
| 错误 | `INVALID_INPUT` 参数或工单绑定不符，`REF_NOT_FOUND` 找不到引用，`CONFLICT` 同节点内容冲突或条件失效，`STORE_UNAVAILABLE` 写入失败。 |

| node.kind | 内容及处理 |
|---|---|
| `input` | 新包归入时填本包新增要求与 `{kind:"package",id:package_id}`，先登记节点再处理。 |
| `result` | 填写成果和引用。新文件先写 `<workspace>/artifacts/`，宿主发布后追加节点。纯文字可传空引用数组。 |
| `blocked` | 写清卡点。申请下载时引用对应的原始附件。 |
| `unblocked` | 材料可用后追加，`refs` 用 `kind:"node"` 引用本单原卡点。 |
| `note` | 引用当轮 `note_id`。Worker 用普通 `write` 写 `<workspace>/notes/{note_id}.json`，宿主核对并发布再追加节点。 |

**执行步骤**

1. 按工单 ID 与节点 ID 核对重复提交。宿主填写 `created_at`。重试提交同一个节点对象，宿主用首次保存的时间补写。
2. 按分支核对引用并发布相应文件，再追加节点。工单原有行保持原字节。

**示例**

```json
[
  {"arguments": {"ticket_id": "B", "node": {"node_id": "B/package-pkg-021", "kind": "input", "text": "请在志愿活动 PPT 最后一页补上集合时间。", "refs": [{"kind": "package", "id": "pkg-021"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "B", "node": {"node_id": "B/3", "kind": "result", "text": "第一版完成，请核对集合地点。", "refs": [{"kind": "artifact", "id": "B/v1.pptx"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "C", "node": {"node_id": "C/3", "kind": "blocked", "text": "需要活动名单，请允许下载活动名单.xlsx。", "refs": [{"kind": "attachment", "id": "raw-020"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "C", "node": {"node_id": "C/5", "kind": "unblocked", "text": "活动名单已下载且可读。", "refs": [{"kind": "node", "id": "C/3"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "B", "node": {"node_id": "B/4", "kind": "note", "text": "本轮笔记已保存。", "refs": [{"kind": "note", "id": "n-017"}]}}, "result": {"code": "OK"}}
]
```

### `mergeTickets`

| 项目 | 约定 |
|---|---|
| 调用签名 | `mergeTickets(args: MergeTicketsArgs): Promise<TicketWriteReceipt \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | 目标工单 Worker → 执行宿主／工单存储。 |
| 调用时机 | 用户指定把一张已有工单并入另一张，目标 Worker 收到该操作并核对两单。 |
| 参数 | `{source_ticket_id:string,target_ticket_id:string,operation_id:string}`。从已保存的原操作取得。 |
| 调用条件 | 两单存在且不同，两个 ID 与原操作一致。调用方是目标 Worker。源单已停止写入，两单均未并出。 |
| 回执 | `{code:"OK" \| "REPLAYED",ticket_id:string}`，`ticket_id` 取目标单 ID。两侧节点都写完才确认。 |
| 错误 | `INVALID_INPUT` 参数或目标 Worker 不符，`REF_NOT_FOUND` 找不到操作或工单，`CONFLICT` 同操作参数冲突或已无法合并，`STORE_UNAVAILABLE` 写入失败。 |

**执行步骤**

1. 宿主按原 `operation_id` 去重，串行核对两单并保存合并计划。先给目标单写 `merge_in`，再给源单写 `merge_out`。计划固定两侧的节点 ID、时间和内容。每侧节点引用原操作与对方工单。
2. 源单通过 `merge_out` 从可见候选中移除。原要求、节点和文件留在原单，沿源单引用回查。中断后用原操作号补缺少的一侧，再返回目标单 ID。已经提交的合并原样重试时返回 `REPLAYED`。

**示例**

```json
[
  {"arguments": {"source_ticket_id": "A", "target_ticket_id": "B", "operation_id": "u-024"}, "result": {"code": "OK", "ticket_id": "B"}}
]
```

### `read`

| 项目 | 约定 |
|---|---|
| 调用签名 | `read(args: DshReadArgs): Promise<{ path: string; offset: number; lines: { number: number; text: string }[]; totalLines: number }>` |
| 调用方 → 责任方 | Router、Worker → DSH 文件工具。宿主按同样路径加载模板和记忆。 |
| 调用时机 | 需要读取命中的工单、节点、模板、记忆、Note 或其他 UTF-8 文本。 |
| 参数 | `{file_path:string,offset?:number,limit?:number}`。`offset` 从 1 起，`offset` 和 `limit` 为正整数，默认行数及上限由 DSH 配置。 |
| 调用条件 | 共享文件按绑定的 `superdot` 取绝对路径。普通相对路径以当前 Session 的 `cwd` 解析。 |
| 回执 | DSH 原生值为 `{path,offset,lines:{number,text}[],totalLines}`，模型看到路径和带行号的文本。 |
| 错误 | 失败由 DSH 返回原生工具错误。 |

**执行步骤**

1. DSH 打开实际文本文件，读取指定行窗口。工单首行是 `TicketHeader`，其后每行一个 `Node`。
2. 下一页从最后读取的行号加 1 继续。查特定节点时按完整 `node_id` 匹配。二进制文件把路径交给对应的 Skill 程序。

**调用示例**

```json
{"file_path": "/hnu/superdot/tickets/B.jsonl"}
```

### `skill`

| 项目 | 约定 |
|---|---|
| 调用签名 | `skill(args: DshSkillArgs): Promise<{ name: string; provider: string; content: string; resourceBase?: SkillResourceBase }>` |
| 调用方 → 责任方 | Router、Worker → DSH Skills。 |
| 调用时机 | 任务明确需要某项 Skill，已从 DSH 目录取得它的名称。 |
| 参数 | `{name:string}`。取目录列出的完整 Skill 名称。 |
| 调用条件 | 宿主将 `superdot/resources/skills` 注册到 DSH。调用时确认该 Skill 在当前角色的目录中可见。 |
| 回执 | 原生值为 `{name,provider,content,resourceBase?}`。本地 Skill 的 `resourceBase` 为 `{kind:"directory",path:string}`。模型看到正文和资源位置。 |
| 错误 | 失败由 DSH 返回原生工具错误。 |

**执行步骤**

1. DSH 按当前 Agent 作用域查目录并加载 `SKILL.md`。
2. 调用方依据返回的资源根定位脚本和模板。资源用相对路径时，基准为 `resourceBase.path`。

**调用示例**

```json
{"name": "ppt"}
```

## 工单、成果和 Note 写入

### 写入工单 JSONL

| 项目 | 约定 |
|---|---|
| 调用签名 | `fs.promises.writeFile(tempPath, jsonl, "utf8")` → `fs.promises.rename(tempPath, ticketPath)` |
| 调用方 → 责任方 | 执行宿主 → 项目文件存储。 |
| 调用时机 | 新建工单，或提交宿主、Worker 的业务节点。 |
| 参数 | 路径 `<superdot>/tickets/{ticket_id}.jsonl`。建单提交 `TicketHeader` 及首个 `Node`，后续传要追加的 `Node`。 |
| 调用条件 | 工单 ID、节点 ID、时间和引用在首次提交前确定，重试沿用原值。宿主代写节点以工单 ID 加 `/` 开头，后缀取节点类型与原包、操作或 Session ID 的稳定键，中断节点用当轮 `note_id` 区分。 |
| 回执 | 文件提交为 `Promise<void>`，完成后可按原路径读回。工单工具的业务回执由宿主处理函数返回。 |
| 错误 | 同一节点 ID 对应不同内容时报 `CONFLICT`，写入或读取故障报 `STORE_UNAVAILABLE`。 |

**执行步骤**

1. 宿主串行写入。建单写头与首节点。追加时把原字节保留为前缀，再加一行 UTF-8 JSON 及换行。
2. 用同目录临时文件完整写入并同步，`rename` 发布后同步父目录。重试先按节点 ID 和内容核对，已存在同内容时跳过写入。
3. 节点发布后，按节点首次引用顺序生成 `package_refs`、`note_refs`，按 `readCandidateTickets` 的规则计算可见性。合并先写目标单再写源单，宿主补齐后才确认。前端和候选查询读取提交后的视图。

```jsonl
{"ticket_id": "B", "title": "志愿活动 PPT", "description": {"text": "按学校模板制作活动说明。"}, "created_at": "2026-11-17T20:30:02+08:00"}
{"node_id": "B/1", "created_at": "2026-11-17T20:30:02+08:00", "kind": "requirement", "text": "请按学校模板做志愿活动 PPT。", "refs": [{"kind": "package", "id": "pkg-017"}, {"kind": "session", "id": "r-017", "role": "router"}]}
```

### 发布成果文件

| 项目 | 约定 |
|---|---|
| 调用签名 | `fs.promises.copyFile(stagedPath, tempPath)` → `fs.promises.rename(tempPath, publishedPath)` |
| 调用方 → 责任方 | 执行宿主 → 项目文件存储。Worker 在本单工作区制作草稿。 |
| 调用时机 | Worker 用 `appendTicketNote` 提交 `result`，节点引用了要发布的新成果。 |
| 参数 | 文件引用 `{kind:"artifact",id:"<ticket_id>/<文件名>"}`。新文件的源为 `<workspace>/artifacts/<文件名>`，目的为 `<superdot>/artifacts/{id}`。 |
| 调用条件 | 草稿完整可读，目标文件名属于本单。引用已有成果时核对实际发布路径。新版用新文件名。 |
| 回执 | 返回实际可读的绝对路径字符串。已有同内容时复用原路径。 |
| 错误 | 已有同路径且内容不同时报 `CONFLICT`，缺少引用文件报 `REF_NOT_FOUND`，存储故障报 `STORE_UNAVAILABLE`。 |

**执行步骤**

1. 在发布计划中固定草稿副本和内容校验值。先写同目录临时文件并同步，再发布为最终路径。
2. 校验发布件可读后追加 `result` 节点。若中断，按已保存的路径、字节和节点 ID 补未完成的步骤。

### 发布 Note

| 项目 | 约定 |
|---|---|
| 调用签名 | `fs.promises.copyFile(stagedPath, tempPath)` → `fs.promises.rename(tempPath, publishedPath)` |
| 调用方 → 责任方 | 执行宿主 → 项目文件存储。Worker 用 `write` 保存当轮草稿。 |
| 调用时机 | 每轮正常收尾，Worker 用 `appendTicketNote` 提交引用当轮 Note 的节点。 |
| 参数 | `Note` 草稿为 `<workspace>/notes/{note_id}.json`，目标为 `<superdot>/memory/notes/{note_id}.json`。 |
| 调用条件 | `note_id`、`ticket_id`、`session_id` 与当轮绑定一致。`created_at` 是首次写入时间，`content` 非空，`evidence_refs` 至少一项且证据存在。 |
| 回执 | 文件发布返回正式 Note 的绝对路径。宿主写完工单的 `note` 引用后确认业务提交。 |
| 错误 | 草稿字段不符报 `INVALID_INPUT`，引用缺失报 `REF_NOT_FOUND`，内容冲突报 `CONFLICT`，存储故障报 `STORE_UNAVAILABLE`。 |

**执行步骤**

1. 读取并校验草稿，固定副本和校验值，按成果发布方式保存正式 JSON 文件。
2. 追加 `note` 节点，`refs` 使用 `{kind:"note",id:note_id}`。中断重试先核对文件和节点，补缺少的一步。

**正式 Note 示例**

```json
{
  "note_id": "n-017",
  "ticket_id": "B",
  "session_id": "worker-B",
  "content": "已制作第一版，集合地点待用户核对。",
  "evidence_refs": [{"kind": "node", "id": "B/3"}, {"kind": "artifact", "id": "B/v1.pptx"}],
  "created_at": "2026-11-17T20:34:01+08:00"
}
```

## 存储数据类型

```ts
type Ref = { id: string }
type StoreError<Code extends string> = { code: Code }
type RawBatch = { code: "OK"; records: RawRecord[]; missing_refs: Ref[] }

type RawRecord = {
  ref: Ref
  source: string
  account_id: string
  conversation_id: string
  message_id: string
  sender_id: string
  sent_at: string
  reply_to_message_id: string | null
  content: string
} & (
  | { type: "text" }
  | { type: "file"; download_state: "NOT_DOWNLOADED" | "DOWNLOADED" | "UNAVAILABLE" }
)

type EvidenceRef =
  | { kind: "package" | "message" | "attachment" | "artifact" | "ticket" | "node" | "note" | "operation"; id: string }
  | { kind: "session"; id: string; role: "router" | "worker" }

type TicketHeader = {
  ticket_id: string
  title: string
  description: { text: string }
  created_at: string
}
type Node = {
  node_id: string
  created_at: string
  kind: "requirement" | "session" | "input" | "feedback" | "result" | "blocked" | "unblocked"
      | "stop" | "resume" | "recover" | "merge_in" | "merge_out" | "confirm" | "note" | "interrupted"
  text: string
  refs: EvidenceRef[]
}
type Ticket = TicketHeader & {
  description: { text: string; visible: 0 | 1 }
  package_refs: Ref[]
  note_refs: Ref[]
  nodes: Node[]
}
type Note = {
  note_id: string
  ticket_id: string
  session_id: string
  created_at: string
  content: string
  evidence_refs: EvidenceRef[]
}
```

| 格式 | 字段约束 |
|---|---|
| `RawRecord` | `sent_at` 为带时区的 ISO 8601。文字的 `content` 为原话。文件的 `content` 为文件名，并给出 `download_state`。 |
| `TicketHeader`、`Node` | 标题、简述和节点 `text` 至少有一个非空白字符。节点 ID 在本单唯一，`created_at` 带时区。工单和 Note 文件名的 ID 匹配 `^[A-Za-z0-9][A-Za-z0-9_-]*$`。 |
| `Ticket` | 从 JSONL 和已提交节点生成。包和笔记索引按引用首次出现的顺序去重。 |
| `Note` | 三个 ID 取当轮绑定，`created_at` 为首次写入时间。`evidence_refs` 至少一项。 |
