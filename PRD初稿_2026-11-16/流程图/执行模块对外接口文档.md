# 执行模块对外接口文档

调用签名使用 TypeScript 记法。HNU 工具传入 JSON 对象，签名中的类型名与本条字段表或 06 的数据定义对应。示例中的 `arguments`、`result` 分别是输入和输出。HTTP 条目的函数签名写明请求与成功响应体，实际调用使用标题中的方法与路径。HNU 工具的业务错误返回 `{code:错误码}`，DSH 原生工具沿用其原生回执。

<a id="dssa-compatibility"></a>

HNU 宿主按 06 的字段处理消息包、工单、节点与原操作。文件工具和 Session 读写沿用 DSH。[06 执行层流程图](06_执行层流程图.svg)

HNU 在 Agent 作用域按角色注册工具。`execute` 校验参数和调用条件，`output.schema` 声明对应的返回分支，`render` 输出 JSON 文本。[DSH 工具注册](../../deepseek-harness/packages/core/tools/src/index.ts#L121)

## 消息接管和 Agent 输入

### `POST /api/router/notify`

| 项目 | 约定 |
|---|---|
| 调用签名 | `notify(request: NotifyRequest): Promise<NotifyReceipt>` |
| 调用方 → 责任方 | 看门狗 → 执行宿主。 |
| 调用时机 | 消息层已保存原文，封包并入队。 |
| 参数 | `{package_ref:{id:string}}`。用当前队首消息包的引用。 |
| 调用条件 | 包已封存，`package_ref.id` 非空。超时继续使用同一包引用。 |
| 回执 | 首次持久接管 HTTP 200，`{code:"OK",package_ref}`。同包重投为 HTTP 200，`code:"REPLAYED"` 且带原包引用。 |
| 错误 | 持久接管失败时回 HTTP 503。回执未知时看门狗保留原包并重投。 |

**执行步骤**

1. 按包 ID 核对已接管记录。首次接收时在宿主本地 SQLite 一并保存包引用、Router 绑定和待执行任务。
2. 保存成功后确认接管，宿主异步派 Router。看门狗核对回执的包 ID 后出队。

**示例**

```json
{
  "arguments": {"package_ref": {"id": "pkg-017"}},
  "result": {"code": "OK", "package_ref": {"id": "pkg-017"}}
}
```

### `RouterBinding` · 宿主交付给 Router

| 项目 | 约定 |
|---|---|
| 调用签名 | `AgentDelivery.send(agent, requestId, JSON.stringify(routerBinding), mode, signal)` |
| 调用方 → 责任方 | 执行宿主 → Router。 |
| 调用时机 | 首次判断已接管的包，或收到该包的用户答复。 |
| 参数 | `{package_id,session_id,superdot,new_ticket_id,notification?}`。前四项是字符串。`notification` 为 `NotificationReplyInput`，仅在交付用户答复时附带。 |
| 调用条件 | `package_id` 为原包。`superdot` 为绝对路径，`new_ticket_id` 由宿主预先固定。Router 回答旧包时沿用原绑定。 |
| 回执 | DSH 收件箱接收绑定。Router 读包并核对旧工单后决定去向。 |

**执行步骤**

1. 首次接管时计算 `session_id="r-"+key("router",package_id)` 和 `new_ticket_id=key("ticket",package_id)`，连同接管记录保存。已有绑定按原值续用。
2. 将绑定作为 JSON 文本交付。Router 用 `package_id` 调用 `readPackage`，有答复时同时读取 `notification`。

**示例 · 首次交付**

```json
{"package_id": "pkg-017", "session_id": "r-017", "superdot": "/hnu/superdot", "new_ticket_id": "B"}
```

**示例 · 用户答复**

```json
{
  "package_id": "pkg-018",
  "session_id": "r-018",
  "superdot": "/hnu/superdot",
  "new_ticket_id": "E",
  "notification": {
    "notification_id": "notice-019",
    "code": "ROUTE_REVIEW",
    "content": "这条实验报告提醒要单独建工单吗？",
    "answer": "create"
  }
}
```

### Router 判断与交付

| 项目 | 约定 |
|---|---|
| 调用顺序 | `readPackage({package_id})` → `readCandidateTickets({})` → `read({file_path})` 查命中工单详情 → 决定去向。 |
| 新建 | 调用 `createTicket`。成功取得工单 ID 后，由宿主派 Worker。 |
| 归入 | 按下方 `routerPackageDelivery` 交给目标 Worker。 |
| 忽略 | 输出纯文本 `ignore` 后结束。宿主完成本包接管。 |
| 存疑 | 保留原包，按现有通知接口向用户确认。 |

### `routerPackageDelivery` · Router 交给目标 Worker

| 项目 | 约定 |
|---|---|
| 调用形式 | Router 在本轮最终回复输出单个 JSON 对象。宿主通过 `AgentDelivery.send(agent, requestId, JSON.stringify(workerBinding), "steer", signal)` 投递。 |
| 调用方 → 责任方 | Router → 执行宿主 → 目标 Worker。 |
| 调用时机 | Router 查完候选与详情，确定当前包归入已有单。 |
| 参数 | `{ticket_id:string,package_ref:{id:string}}`。工单号取命中的候选，包 ID 取当前绑定。 |
| 调用条件 | 最终回复可解析，目标工单仍可见。校验失败时，宿主保留待处理的原包并重新核对候选。 |
| 回执 | 宿主保存待投递记录后接管交付。Worker 调用 `appendTicketNote` 成功后，工单中可查到该包的输入节点。 |

**执行步骤**

1. 宿主解析本轮正常结束的最终回复，按包 ID 保存目标工单与待投递记录。为该包预备目标单的 `input_node_id`，重投沿用同一投递 ID 和节点 ID。
2. 交付 `WorkerBinding.input`。Worker 读包，再用 `appendTicketNote` 登记输入，随后处理。两张已有工单的合并由用户从工单补充／反馈入口指定。

```json
{"ticket_id": "B", "package_ref": {"id": "pkg-021"}}
```

### `WorkerBinding` · 宿主交付给 Worker

| 项目 | 约定 |
|---|---|
| 调用签名 | `AgentDelivery.send(agent, requestId, JSON.stringify(workerBinding), mode, signal)` |
| 调用方 → 责任方 | 执行宿主 → 当前工单的 Worker。 |
| 调用时机 | 首次派工、正在处理时收到补充，或有新输入需要接续。 |
| 参数 | `{ticket_id,session_id,superdot,ticket_path,workspace,note_id,input}`。除 `input` 外均为字符串。各输入分支见下表。 |
| 调用条件 | `session_id=worker-<ticket_id>`。三个路径字段均为绝对路径。`ticket_path` 从 `superdot` 和工单 ID 得到，`workspace` 从部署工作区根与本单 ID 得到。每轮在投递前分配并保存 `note_id`。 |
| 回执 | DSH 收件箱接收绑定。业务写入分别以 `appendTicketNote` 或 `mergeTickets` 的回执为准。 |

| input.kind | 字段 | 接收后读取 |
|---|---|---|
| `package` | `package_ref:Ref`，`input_node_id:string` 指首个 `requirement`，或归入预备的 `input` 节点 ID。 | 用 `readPackage({package_id:input.package_ref.id})` 读原文，再读 `ticket_path` 核对该节点。已记录同一包时沿用原节点，待登记者用交付的 ID 追加。 |
| `operation` | `operation_id:string`。补充、反馈、恢复、接续带 `input_node_id`。指定合并交付时只有 `operation_id`。 | 用 `read` 打开 `<superdot>/operations/{encodeURIComponent(operation_id)}.json`。反馈或异常接续所选的旧节点 ID 在原请求里。 |
| `notification` | `notification:NotificationReplyInput`。 | 按原 `content`、`answer` 和适用的 `node_id` 处理。 |
| `download` | `notification_id`、`operation_id`、`input_node_id`、`blocked_node_id`、`raw_id`、`file_path` 均为字符串。 | 从 `file_path` 打开副本，按 `raw_id` 查文件记录，确认可用后以原 `blocked_node_id` 解除卡点。 |

**执行步骤**

1. 新增包归入时先保存投递待办，节点由 Worker 追加。用户操作先保存原请求。已有活跃 Worker 时投递到该实例，旧执行退出后续用本单 Session。
2. 同一轮内新输入替换当前 `input`，沿用本轮笔记号。Worker 按分支取回正文、证据或文件。

**示例 · 首次派工**

```json
{
  "ticket_id": "B",
  "session_id": "worker-B",
  "superdot": "/hnu/superdot",
  "ticket_path": "/hnu/superdot/tickets/B.jsonl",
  "workspace": "/hnu/work/B",
  "note_id": "n-017",
  "input": {"kind": "package", "package_ref": {"id": "pkg-017"}, "input_node_id": "B/1"}
}
```

**示例 · 下载完成的 input**

```json
{
  "kind": "download",
  "notification_id": "notice-dl-020",
  "operation_id": "u-dl-020",
  "input_node_id": "C/4",
  "blocked_node_id": "C/3",
  "raw_id": "raw-020",
  "file_path": "/hnu/superdot/downloads/raw-020/活动名单.xlsx"
}
```

## 工单写入工具

注册用的参数和返回类型取 06 的 `contract.interfaces` 与 `contract.schema.$defs`。工单 ID 和节点 ID 的各段以 ASCII 字母或数字开头，后续可用 ASCII 字母、数字、下划线和连字符。[06 执行层流程图](06_执行层流程图.svg)

### `createTicket`

| 项目 | 约定 |
|---|---|
| 调用签名 | `createTicket(args: CreateTicketArgs): Promise<TicketWriteReceipt \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | Router → 执行宿主／工单存储。 |
| 调用时机 | 已查过全部可见候选并读完匹配详情，确认本包需要新建工单。 |
| 参数 | `{package_id,ticket_id,title,description,requirement}`，均为非空字符串。`package_id` 取当前包，`ticket_id` 取 Router 输入的 `new_ticket_id`。 |
| 调用条件 | 本包已接管。本轮已完成 `readCandidateTickets({})`，空候选返回 `[]` 时也算完成检索。 |
| 回执 | `{code:"OK" \| "REPLAYED",ticket_id:string}`，`ticket_id` 为本次工单号。 |
| 错误 | `INVALID_INPUT` 参数或绑定不符，`REF_NOT_FOUND` 找不到原包，`CONFLICT` 同包建单参数冲突，`STORE_UNAVAILABLE` 写入失败。 |

**执行步骤**

1. 按包 ID 核对已有建单记录。宿主保存工单头，`description` 写入 `description.text`。首个 `requirement` 的正文取 `requirement`，引用原包和 Router Session。
2. 工单头、首节点和待派工输入都保存后回执。宿主用工单 ID、原包引用和首节点 ID 启动 Worker。原样重试沿用工单号与节点。

**示例**

```json
[
  {"arguments": {"package_id": "pkg-017", "ticket_id": "B", "title": "志愿活动 PPT", "description": "按学校模板制作活动说明。", "requirement": "请按学校模板做志愿活动 PPT。"}, "result": {"code": "OK", "ticket_id": "B"}}
]
```

### `appendTicketNote`

| 项目 | 约定 |
|---|---|
| 调用签名 | `appendTicketNote(args: AppendTicketNoteArgs): Promise<CommitAck \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | 当前工单 Worker → 执行宿主／工单存储。 |
| 调用时机 | 给本单登记归入的新包、成果、卡点、解除记录或本轮 Note。 |
| 参数 | `{ticket_id:string,node:{node_id,kind,text,refs}}`。`node` 使用工单节点字段。`text` 非空，`refs:EvidenceRef[]`。 |
| 调用条件 | `ticket_id` 是本单。节点 ID 以本单 ID 加 `/` 开头，通常由 Worker 预先分配。归入包时使用交付的 `input_node_id` 与 `package_ref.id`。引用须能回查。 |
| 回执 | `{code:"OK" \| "REPLAYED"}`。文件和该节点都提交后确认。 |
| 错误 | `INVALID_INPUT` 参数或工单绑定不符，`REF_NOT_FOUND` 找不到引用，`CONFLICT` 同节点内容冲突或条件失效，`STORE_UNAVAILABLE` 写入失败。 |

| node.kind | 内容及处理 |
|---|---|
| `input` | 新包归入时填本包新增要求与 `{kind:"package",id:package_id}`，先登记节点再处理。 |
| `result` | 填写成果和引用。新文件先写 `<workspace>/artifacts/`，宿主发布后追加节点。纯文字可传空引用数组。 |
| `blocked` | 写清卡点。申请下载时引用对应的原始附件。 |
| `unblocked` | 材料可用后追加，`refs` 用 `kind:"node"` 引用本单原卡点。 |
| `note` | 引用当轮 `note_id`。Worker 用普通 `write` 写 `<workspace>/notes/{note_id}.json`，宿主核对并发布再追加节点。 |

**执行步骤**

1. 按工单 ID 与节点 ID 核对重复提交。宿主填写 `created_at`。重试提交同一个节点对象，宿主用首次保存的时间补写。
2. 按分支核对引用并发布相应文件，再追加节点。工单原有行保持原字节。

**示例**

```json
[
  {"arguments": {"ticket_id": "B", "node": {"node_id": "B/package-pkg-021", "kind": "input", "text": "请在志愿活动 PPT 最后一页补上集合时间。", "refs": [{"kind": "package", "id": "pkg-021"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "B", "node": {"node_id": "B/3", "kind": "result", "text": "第一版完成，请核对集合地点。", "refs": [{"kind": "artifact", "id": "B/v1.pptx"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "C", "node": {"node_id": "C/3", "kind": "blocked", "text": "需要活动名单，请允许下载活动名单.xlsx。", "refs": [{"kind": "attachment", "id": "raw-020"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "C", "node": {"node_id": "C/5", "kind": "unblocked", "text": "活动名单已下载且可读。", "refs": [{"kind": "node", "id": "C/3"}]}}, "result": {"code": "OK"}},
  {"arguments": {"ticket_id": "B", "node": {"node_id": "B/4", "kind": "note", "text": "本轮笔记已保存。", "refs": [{"kind": "note", "id": "n-017"}]}}, "result": {"code": "OK"}}
]
```

### `mergeTickets`

| 项目 | 约定 |
|---|---|
| 调用签名 | `mergeTickets(args: MergeTicketsArgs): Promise<TicketWriteReceipt \| StoreError<"INVALID_INPUT" \| "REF_NOT_FOUND" \| "CONFLICT" \| "STORE_UNAVAILABLE">>` |
| 调用方 → 责任方 | 目标工单 Worker → 执行宿主／工单存储。 |
| 调用时机 | 用户指定把一张已有工单并入另一张，目标 Worker 收到该操作并核对两单。 |
| 参数 | `{source_ticket_id:string,target_ticket_id:string,operation_id:string}`。从已保存的原操作取得。 |
| 调用条件 | 两单存在且不同，两个 ID 与原操作一致。调用方是目标 Worker。源单已停止写入，两单均未并出。 |
| 回执 | `{code:"OK" \| "REPLAYED",ticket_id:string}`，`ticket_id` 取目标单 ID。两侧节点都写完才确认。 |
| 错误 | `INVALID_INPUT` 参数或目标 Worker 不符，`REF_NOT_FOUND` 找不到操作或工单，`CONFLICT` 同操作参数冲突或已无法合并，`STORE_UNAVAILABLE` 写入失败。 |

**执行步骤**

1. 宿主按原 `operation_id` 去重，串行核对两单并保存合并计划。先给目标单写 `merge_in`，再给源单写 `merge_out`。计划固定两侧的节点 ID、时间和内容。每侧节点引用原操作与对方工单。
2. 源单通过 `merge_out` 从可见候选中移除。原要求、节点和文件留在原单，沿源单引用回查。中断后用原操作号补缺少的一侧，再返回目标单 ID。已经提交的合并原样重试时返回 `REPLAYED`。

**示例**

```json
[
  {"arguments": {"source_ticket_id": "A", "target_ticket_id": "B", "operation_id": "u-024"}, "result": {"code": "OK", "ticket_id": "B"}}
]
```

### `POST /api/tickets/actions` · 工单操作

| 项目 | 约定 |
|---|---|
| 调用签名 | `steer(request: SteerRequest): Promise<ActionReceipt>` |
| 调用方 → 责任方 | 前端 → 执行宿主。 |
| 调用时机 | 用户提交补充、反馈、终止、恢复、异常接续或指定合并。 |
| 参数 | 必填字符串 `operation`、`operation_id`。各分支额外字段见表。原请求类型为 `SteerRequest`。 |
| 调用条件 | `operation_id` 由前端首次提交前确定。附件先存原始文件记录，填写其 `Ref`。重复提交使用原请求。 |
| 回执 | 首次持久接收为 HTTP 202，`{code:"ACCEPTED",operation_id,ticket_id}`。重投为 HTTP 200、原字段及 `code:"REPLAYED"`。合并的 `ticket_id` 为目标单。 |
| 错误 | 同一操作 ID 提交不同内容回 HTTP 409、`{code:"CONFLICT"}`。异常接续的中断已经消费时按原操作核对重放。 |

| operation | 参数及条件 | 宿主处理 |
|---|---|---|
| `supplement` | `ticket_id`，`text` 或非空 `attachment_refs:Ref[]` 至少一项。 | 追加 `input`，保留原话及操作、附件引用。只有附件时用文件名说明。 |
| `feedback` | 同补充，另有本单成果的 `node_id`。 | 追加 `feedback`，引用原成果、操作和适用的附件。 |
| `stop` | `ticket_id`。 | 停派、冻结旧执行新写入。提交 `stop`，更新可见性并取消旧执行。保留已接管的原输入。 |
| `resume` | `ticket_id`。本单由用户终止，旧执行已退出。 | 追加 `resume`，恢复可见性，续用本单原 Session。首次派工按本单绑定创建。 |
| `recover` | `ticket_id` 和本单最近仍待接续的 `interrupted` 节点 `node_id`。本单可见，旧执行已退出。 | 追加 `recover` 引用原操作、原中断节点，从中断节点的会话引用接续。 |
| `merge` | `source_ticket_id`、`target_ticket_id`。两单存在且不同，源单可并出，目标单可派工。 | 保存合并操作后交目标 Worker，目标单同时处理一条合并指令。提交双方节点后源单从候选中移除。 |

**执行步骤**

1. 按 `operation_id` 去重并校验分支条件，保存原请求以及后续待办。持久接收后确认。
2. 补充、反馈、恢复和异常接续先提交本单节点，再将原操作 ID 与新增的 `input_node_id` 交付 Worker。
3. 合并时暂停源单派工，等旧执行退出写入，再把原操作交付目标 Worker。目标 Worker 读取原操作文件，调用 `mergeTickets`。目标单提前结束且尚未开始提交时，释放源单并通知合并未完成。已保存的提交计划按两单原节点 ID 补齐。

**示例 · 成果反馈**

```json
{
  "arguments": {
    "operation": "feedback",
    "operation_id": "u-020",
    "ticket_id": "B",
    "node_id": "B/3",
    "text": "集合地点改为图书馆南门。"
  },
  "result": {"code": "ACCEPTED", "operation_id": "u-020", "ticket_id": "B"}
}
```

**示例 · 指定合并**

```json
{
  "arguments": {"operation": "merge", "operation_id": "u-024", "source_ticket_id": "A", "target_ticket_id": "B"},
  "result": {"code": "ACCEPTED", "operation_id": "u-024", "ticket_id": "B"}
}
```

**示例 · 异常接续请求**

```json
{"operation": "recover", "operation_id": "u-023", "ticket_id": "B", "node_id": "B/9"}
```

### `POST /api/tickets/actions` · 确认成果

| 项目 | 约定 |
|---|---|
| 调用签名 | `confirm(request: ConfirmRequest): Promise<ConfirmReceipt>` |
| 调用方 → 责任方 | 前端 → 工单程序。 |
| 调用时机 | 用户确认工单中的某项阶段成果。 |

| 调用方 → 责任方 | Router、Worker、Dreamer、DataBase 等已登记来源 → 通知服务。 |

| 参数 | 必填 `notification_id`、`origin`、`code`、`content`、`occurred_at`。选填 `options`、`package_ref`、`ticket_id`、`session_id`、`node_id`、`state`。字段类型见下方工具定义。 |

| 参数 | `{raw_id:string}`。取 `type:"file"` 的原始记录 `ref.id`，ID 至少含一个非空白字符。 |
| 调用条件 | 文件待下载或已下载副本缺失时，宿主按当前工单及该 `raw_id` 校验用户的 `allow` 回执。 |
| 回执 | 成功返回文件副本的实际绝对路径字符串，Worker 可直接打开。 |
| 错误 | `INVALID_INPUT` 为参数不符或记录为文字，`REF_NOT_FOUND` 为原件不存在，`AUTHORIZATION_REQUIRED` 为缺少许可，`CONFLICT` 为无法取回，`STORE_UNAVAILABLE` 为临时读写或来源故障。 |

**执行步骤**

1. 按 `raw_id` 查文件记录。状态为 `DOWNLOADED` 且副本可读时，直接返回已存路径。状态为 `UNAVAILABLE` 时返回 `CONFLICT`。
2. 需要下载时先校验授权，再由消息层按来源索引下载。同一原件的并发请求复用一次下载。
3. 完整副本落盘并可读后保存路径和 `DOWNLOADED`。已过期等无法取回时记为 `UNAVAILABLE`。

**工具定义**

```json
{
  "name": "askDownloadFile",
  "description": "按文件记录 ID 获取已授权文件的本地绝对路径。",
  "parameters": {
    "type": "object",
    "properties": {"raw_id": {"type": "string", "minLength": 1, "pattern": "\\S"}},
    "required": ["raw_id"],
    "additionalProperties": false
  }
}
```

**示例**

```json
{"arguments": {"raw_id": "raw-018"}, "result": "/hnu/superdot/downloads/raw-018/志愿活动模板.pptx"}
```

## 工单、成果和 Note 写入

### 写入工单 JSONL

| 项目 | 约定 |
|---|---|
| 调用签名 | `fs.promises.writeFile(tempPath, jsonl, "utf8")` → `fs.promises.rename(tempPath, ticketPath)` |
| 调用方 → 责任方 | 执行宿主 → 项目文件存储。 |
| 调用时机 | 新建工单，或提交宿主、Worker 的业务节点。 |
| 参数 | 路径 `<superdot>/tickets/{ticket_id}.jsonl`。建单提交 `TicketHeader` 及首个 `Node`，后续传要追加的 `Node`。 |
| 调用条件 | 工单 ID、节点 ID、时间和引用在首次提交前确定，重试沿用原值。宿主代写节点以工单 ID 加 `/` 开头，后缀取节点类型与原包、操作或 Session ID 的稳定键，中断节点用当轮 `note_id` 区分。 |
| 回执 | 文件提交为 `Promise<void>`，完成后可按原路径读回。工单工具的业务回执由宿主处理函数返回。 |
| 错误 | 同一节点 ID 对应不同内容时报 `CONFLICT`，写入或读取故障报 `STORE_UNAVAILABLE`。 |

**执行步骤**

1. 宿主串行写入。建单写头与首节点。追加时把原字节保留为前缀，再加一行 UTF-8 JSON 及换行。
2. 用同目录临时文件完整写入并同步，`rename` 发布后同步父目录。重试先按节点 ID 和内容核对，已存在同内容时跳过写入。
3. 节点发布后，按节点首次引用顺序生成 `package_refs`、`note_refs`，按 `readCandidateTickets` 的规则计算可见性。合并先写目标单再写源单，宿主补齐后才确认。前端和候选查询读取提交后的视图。

```jsonl
{"ticket_id": "B", "title": "志愿活动 PPT", "description": {"text": "按学校模板制作活动说明。"}, "created_at": "2026-11-17T20:30:02+08:00"}
{"node_id": "B/1", "created_at": "2026-11-17T20:30:02+08:00", "kind": "requirement", "text": "请按学校模板做志愿活动 PPT。", "refs": [{"kind": "package", "id": "pkg-017"}, {"kind": "session", "id": "r-017", "role": "router"}]}
```

### 发布成果文件

| 项目 | 约定 |
|---|---|
| 调用签名 | `fs.promises.copyFile(stagedPath, tempPath)` → `fs.promises.rename(tempPath, publishedPath)` |
| 调用方 → 责任方 | 执行宿主 → 项目文件存储。Worker 在本单工作区制作草稿。 |
| 调用时机 | Worker 用 `appendTicketNote` 提交 `result`，节点引用了要发布的新成果。 |
| 参数 | 文件引用 `{kind:"artifact",id:"<ticket_id>/<文件名>"}`。新文件的源为 `<workspace>/artifacts/<文件名>`，目的为 `<superdot>/artifacts/{id}`。 |
| 调用条件 | 草稿完整可读，目标文件名属于本单。引用已有成果时核对实际发布路径。新版用新文件名。 |
| 回执 | 返回实际可读的绝对路径字符串。已有同内容时复用原路径。 |
| 错误 | 已有同路径且内容不同时报 `CONFLICT`，缺少引用文件报 `REF_NOT_FOUND`，存储故障报 `STORE_UNAVAILABLE`。 |

**执行步骤**

1. 在发布计划中固定草稿副本和内容校验值。先写同目录临时文件并同步，再发布为最终路径。
2. 校验发布件可读后追加 `result` 节点。若中断，按已保存的路径、字节和节点 ID 补未完成的步骤。

### 发布 Note

| 项目 | 约定 |
|---|---|
| 调用签名 | `fs.promises.copyFile(stagedPath, tempPath)` → `fs.promises.rename(tempPath, publishedPath)` |
| 调用方 → 责任方 | 执行宿主 → 项目文件存储。Worker 用 `write` 保存当轮草稿。 |
| 调用时机 | 每轮正常收尾，Worker 用 `appendTicketNote` 提交引用当轮 Note 的节点。 |
| 参数 | `Note` 草稿为 `<workspace>/notes/{note_id}.json`，目标为 `<superdot>/memory/notes/{note_id}.json`。 |
| 调用条件 | `note_id`、`ticket_id`、`session_id` 与当轮绑定一致。`created_at` 是首次写入时间，`content` 非空，`evidence_refs` 至少一项且证据存在。 |
| 回执 | 文件发布返回正式 Note 的绝对路径。宿主写完工单的 `note` 引用后确认业务提交。 |
| 错误 | 草稿字段不符报 `INVALID_INPUT`，引用缺失报 `REF_NOT_FOUND`，内容冲突报 `CONFLICT`，存储故障报 `STORE_UNAVAILABLE`。 |

**执行步骤**

1. 读取并校验草稿，固定副本和校验值，按成果发布方式保存正式 JSON 文件。
2. 追加 `note` 节点，`refs` 使用 `{kind:"note",id:note_id}`。中断重试先核对文件和节点，补缺少的一步。

**正式 Note 示例**

```json
{
  "note_id": "n-017",
  "ticket_id": "B",
  "session_id": "worker-B",
```

### `ctx.agentLoop.createAgent`

| 项目 | 约定 |
|---|---|
| 调用签名 | `ctx.agentLoop.createAgent(ownerCtx: Context, options: CreateAgentOptions): Promise<AgentHandle>` |
| 调用方 → 责任方 | 执行宿主 → DSH Agent 循环。 |
| 调用时机 | 本包或本单首次执行，按原 ID 查询确实没有已存 Session。 |
| 参数 | `createAgent(ownerCtx,{sessionId,meta:{cwd},agentOptions,setup})`。ID 由宿主绑定，`cwd` 取 Router 的 `superdot` 或 Worker 的 `workspace`。 |
| 调用条件 | 同 Session 的创建、接续、释放由宿主串行处理。模型设置取部署配置。 |
| 回执 | `Promise<AgentHandle>`，句柄包含 `agent` 和 `dispose()`。 |

**执行步骤**

1. 在 `setup(agentCtx,agent)` 中加载角色预设、模板和顶层记忆，注册该角色的工具。
2. 首次 Worker 开工向工单追加 `session` 节点，引用实际 `session_id` 及 `role:"worker"`。完成后交付第一条输入。

[DSH CreateAgentOptions](../../deepseek-harness/packages/core/agent/src/index.ts#L66)

### `ctx.agentLoop.resume`

| 项目 | 约定 |
|---|---|
| 调用签名 | `ctx.agentLoop.resume(ownerCtx: Context, options: ResumeAgentOptions): Promise<AgentHandle>` |
| 调用方 → 责任方 | 执行宿主 → DSH Agent 循环。 |
| 调用时机 | 既有 Session 有后续输入，旧 Agent 已退出。 |
| 参数 | `resume(ownerCtx,{resumeSessionId,agentOptions,setup})`。使用原 Session ID。 |
| 调用条件 | 已存 Session 可读，旧执行已释放写句柄。用户恢复或异常接续须先提交相应节点。 |
| 回执 | `Promise<AgentHandle>`，Session 保留原 ID 和历史。 |

**执行步骤**

1. 恢复 DSH Session，在新作用域重新挂载角色工具与模板。Worker 启动新轮时准备新的 `note_id`。
2. 用稳定消息 ID 核对历史和收件箱。历史中已取得的输入继续按原记录回查。仅在还原收件箱中的 HNU 输入先保留宿主待办，用 `agent.inbox.remove` 移出旧项，再按原键送入并唤醒。新轮重新绑定尚未取走的输入。

[DSH ResumeAgentOptions](../../deepseek-harness/packages/core/agent/src/index.ts#L127) · [恢复收件箱](../../deepseek-harness/packages/core/agent-loop/tests/resume.spec.ts#L1014)

### `AgentDelivery.send`

| 项目 | 约定 |
|---|---|
| 调用签名 | `AgentDelivery.send(agent: Agent, requestId: string, text: string, mode: "queue" \| "steer", signal: AbortSignal): Promise<void>` |
| 调用方 → 责任方 | 执行宿主 → Router 或 Worker 的 DSH 收件箱。 |
| 调用时机 | Agent 可用且输入引用已经保存，需要交付绑定。 |
| 参数 | `send(agent,requestId,text,mode,signal)`。`text` 是 `RouterBinding` 或 `WorkerBinding` 的 JSON。当前步补充用 `mode="steer"`，新轮用 `mode="queue"`。 |
| 调用条件 | `requestId=key("delivery",session_id,输入类型,原始ID)`。原 ID 从包、操作或通知引用取得。`download` 使用补充操作 ID，同轮重投沿用原键和文本。 |
| 回执 | `Promise<void>`。投递并刷新 DSH 会话存储后完成。 |

**执行步骤**

1. 按稳定消息 ID 查历史及收件箱，复用 DSSA 的去重和投递代码。当前轮用 `agent.steer`，新轮用 `agent.followup`。
2. 等待 `flush()`。宿主用 `agent/inbox/claimed` 或原生 `user/message` 关联 Agent 已取走的输入。

[DSSA 投递函数](../../dsh-superagent-prototype/src/app/delivery.ts#L65)

### `agent.cancel`

| 项目 | 约定 |
|---|---|
| 调用签名 | `agent.cancel(cause: AgentCancelCause, options?: CancelOptions): void` |
| 调用方 → 责任方 | 执行宿主 → 当前 DSH Agent。 |
| 调用时机 | 用户终止工单，或合并前结束源单的活动执行。 |
| 参数 | `cancel({kind:"user"},{keepInbox:false})`。 |
| 调用条件 | 先冻结该执行的新业务提交，保留宿主已接管的输入。已接受的提交按原计划完成。 |

**执行步骤**

1. DSH 取消当前活动。宿主等待后台任务退出、刷新会话并释放句柄，随后才允许本单接续。

[DSH cancel](../../deepseek-harness/packages/core/agent/src/runtime-types.ts#L205)

### `AgentHandle.dispose`

| 项目 | 约定 |
|---|---|
| 调用签名 | `handle.dispose(): Promise<void>` |
| 调用方 → 责任方 | 执行宿主 → DSH Agent 循环。 |
| 调用时机 | 本轮正常收尾，或终止、异常后释放旧执行。 |
| 参数 | `dispose()`，使用宿主自己持有的原句柄。 |
| 调用条件 | 正常收尾先确认 Worker 当轮 Note 已提交，Router 已完成本包处理，等用户答复时先保存通知和原包关联。新输入留给宿主待办。 |
| 回执 | `Promise<void>`。完成后释放 Agent 及其写入资格，已有 Session 可续用。 |

**执行步骤**

1. 等 `agent.whenIdle()`、后台工作退出和会话 `flush()`，再释放句柄。
2. 异常退出先补已接受的提交。未正常收尾的 Worker 用本轮固定键记录 `interrupted` 并关联原 Session，用户终止时以已提交的 `stop` 为准。Router 出错且无决定或待答复通知时保留原包，按原 Session 复判。

[DSH AgentHandle](../../deepseek-harness/packages/core/agent/src/index.ts#L147)

## 存储数据类型

```ts
type Ref = { id: string }
type StoreError<Code extends string> = { code: Code }
type RawBatch = { code: "OK"; records: RawRecord[]; missing_refs: Ref[] }

type RawRecord = {
  ref: Ref
  source: string
  account_id: string
  conversation_id: string
  message_id: string
  sender_id: string
  sent_at: string
  reply_to_message_id: string | null
  content: string
} & (
  | { type: "text" }
  | { type: "file"; download_state: "NOT_DOWNLOADED" | "DOWNLOADED" | "UNAVAILABLE" }
)

type EvidenceRef =
  | { kind: "package" | "message" | "attachment" | "artifact" | "ticket" | "node" | "note" | "operation"; id: string }
  | { kind: "session"; id: string; role: "router" | "worker" }

type TicketHeader = {
  ticket_id: string
  title: string
  description: { text: string }
  created_at: string
}
type Node = {
  node_id: string
  created_at: string
  kind: "requirement" | "session" | "input" | "feedback" | "result" | "blocked" | "unblocked"
      | "stop" | "resume" | "recover" | "merge_in" | "merge_out" | "confirm" | "note" | "interrupted"
  text: string
  refs: EvidenceRef[]
}
type Ticket = TicketHeader & {
  description: { text: string; visible: 0 | 1 }
  package_refs: Ref[]
  note_refs: Ref[]
  nodes: Node[]
}
type Note = {
  note_id: string
  ticket_id: string
  session_id: string
  created_at: string
  content: string
  evidence_refs: EvidenceRef[]
}
```

| 格式 | 字段约束 |
|---|---|
| `RawRecord` | `sent_at` 为带时区的 ISO 8601。文字的 `content` 为原话。文件的 `content` 为文件名，并给出 `download_state`。 |
| `TicketHeader`、`Node` | 标题、简述和节点 `text` 至少有一个非空白字符。节点 ID 在本单唯一，`created_at` 带时区。工单和 Note 文件名的 ID 匹配 `^[A-Za-z0-9][A-Za-z0-9_-]*$`。 |
| `Ticket` | 从 JSONL 和已提交节点生成。包和笔记索引按引用首次出现的顺序去重。 |
| `Note` | 三个 ID 取当轮绑定，`created_at` 为首次写入时间。`evidence_refs` 至少一项。 |

## 通知数据类型

```ts
type NotificationReplyInput = {
  notification_id: string
  code: string
  content: string
  answer?: string
  node_id?: string
}

type NoticeItem = {
  id: string
  origin: string
  code: string
  content: string
  occurred_at: string
  state: "pending" | "handled"
  options?: { value: string; label: string }[]
  package_ref?: Ref
  ticket_id?: string
  session_id?: string
  node_id?: string
  answer?: string

```

`NotificationReplyInput` 中 `code` 和 `content` 取发布原文，`answer` 取用户处理结果。`NoticeItem.id` 取通知 ID，`answer` 仅在已处理且该通知须答复时返回。
